# Scenes: structure, identity and revision mapping

Resolution of Wayfinder ticket #52. Vocabulary is in [`GLOSSARY.md`](../../GLOSSARY.md). The identity trade-off is [ADR 0011](../adr/0011-scene-identity-is-the-container-block-id-and-mapping-precedes-id-assignment.md). This is a design contract, not a schema; field names are illustrative.

Authority: Constitution §§4.3–4.4, 5.1–5.2, 5.6, 7.1, 16 (principles 3, 4, 11); [`CREATOR-RATIFICATION-RECORD.md`](../product/CREATOR-RATIFICATION-RECORD.md) R1, R2, R3, M1, M3; [`CREATOR-RATIFICATION-RECORD-2.md`](../product/CREATOR-RATIFICATION-RECORD-2.md) D52, P7, P9, X5 (controls where it differs; see the closing section); [`DOMAIN-MODEL.md`](DOMAIN-MODEL.md) §4.1; [`STORY-DOCUMENTS.md`](STORY-DOCUMENTS.md) §§2.2, 8; [`LINEAGE-AND-STALENESS.md`](LINEAGE-AND-STALENESS.md); [`../ai/AI-RESPONSIBILITY-MAP.md`](../ai/AI-RESPONSIBILITY-MAP.md). V1 is cited only as failure evidence (legacy 06 §8; legacy 04 §8; legacy 10 §§5, 7).

No `CONSTITUTION AMENDMENT REQUIRED`. Nothing here conflicts with a CORE or IMPORTANT requirement. The "may not reopen" items are all kept: one human-editable Master Narrative, no camera direction in it, no scene silently deleted with its work.

## 1. V1 failures and the V2 rule that answers each

| V1 failure | V2 rule |
|---|---|
| Identity was `slug:number`, then number alone (legacy 06 §8.3 M1, M2) | Identity is an opaque id minted by the server. Heading, number and position are labels and never identity. |
| Unmatched scenes were hard-deleted with seven cascades (06 §8.3 D1, §8.4; 04 §8) | Retire, never delete. Nothing attached to a scene is touched when it leaves the narrative. |
| An insert or delete re-pointed later scenes' work to different text (06 §8.3 D3) | Position is never an identity source. Work follows its anchored text, and anything that cannot be decided from ids is asked about. |
| Deletes failed silently; there was no transaction (06 §8.2) | A mapping is applied as one atomic Revision with its Decision; it fully applies or does not apply. |
| The dialog promised `continuity_broken` marking that no code did (06 §8.3) | Marking is derived from lineage ([`LINEAGE-AND-STALENESS.md`](LINEAGE-AND-STALENESS.md) §3), not promised by copy. |
| About eight disagreeing heading parsers (06 §8.6) | Structure is explicit container blocks. No identity or boundary is recovered from prose by pattern matching. |
| Lines before the first heading were dropped (06 §8.1) | Nothing is dropped (§5.4). |

## 2. Representation and identity

### 2.1 Decision

**A Scene is the identity of a `scene` container block of the Master Narrative.** The Scene id is the container block id from [`STORY-DOCUMENTS.md`](STORY-DOCUMENTS.md) §2.2. There is no second id and no mapping table between them. The trade-off is in ADR 0011.

```diagram
Master Narrative (Document)
  blocks, in story order (list order)
    scene [S12]  attrs: heading (label), duration { seconds, provenance }
       setting | action | state_change | dialogue [D40]     children, own ids
    scene [S13]  ...

Scene S12 (production owner, keyed by that id)
   shots ─ frames ─ takes      hang off S12, never off position or text
```

- **Boundaries are explicit.** Every narrative block lives inside exactly one scene. A boundary is where one container ends and the next begins. Code never infers one from prose.
- **A Scene's state is derived from the head Revision.** It is **active** if a container with its id exists in the head Revision, else **retired**. No stored flag. A retired Scene keeps every Shot, Frame, Take, anchor and Decision attached.
- **Order** is container order in the head Revision. **Number** ("Scene 4") is a label counting active scenes only. A retired scene shows "formerly 4, <heading>".
- **Heading is a label**, an editable field of runs. Its machine meaning (place, time) comes from setting Mentions ([`ENTITIES-AND-LOOKS.md`](ENTITIES-AND-LOOKS.md) §§3, 5), not from parsing it.
- **Duration.** Each scene has an approximate duration: a number with a provenance tag, set by drafting or conversion as an AI estimate, or by the creator. It is part of the narrative and is edited as a Revision. It is re-estimated only when that scene is regenerated by an AI operation, and a creator-set value is protected like a creator run. Nothing recomputes it silently, so it needs no marker. The sum against the intended runtime is displayed, never blocking (AI map §4.3). Shot durations (#55) are shown beside it and are independent.
- **Identity is assigned when a container first appears** in any Revision (draft, conversion, import, creator insert or split), not at acceptance. Before acceptance nothing is produced from scenes, so structural changes need no confirmation. Acceptance (Constitution §7.1) makes the active scenes the production list. There is no "re-approve" step that re-extracts scenes: production always reads the head Revision's active scenes.
- **Zero scenes** is allowed in a draft. Acceptance requires at least one.
- **Above scenes.** Acts, sequences and episodes (LATER) can wrap scene containers without changing any scene id.

### 2.2 Block lifecycle at scene level

Inherited from [`STORY-DOCUMENTS.md`](STORY-DOCUMENTS.md) §2.2 and fixed here:

| Operation | Ids |
|---|---|
| **Insert** a scene | New container, new id. |
| **Delete** a scene | Container retired; its children retired with it; recoverable from any earlier Revision. |
| **Reorder** | Ids unchanged. |
| **Split** at a point | The upper part keeps the id. The lower part gets a new id with `split_from`. Children keep their ids and move with their text. |
| **Merge** two adjacent scenes | The earlier keeps the id. The later is retired with `merged_into`. Children keep their ids and move with their text. |
| **Move a passage** between scenes (cut and paste inside the app) | Moved, ids unchanged. Pasting text copied from elsewhere creates new blocks. |
| **Rewrite** inside a scene | Container id unchanged. Children follow the whole-block rule of STORY-DOCUMENTS §5. |
| **Regenerate this scene** | Container id unchanged. |

### 2.3 Who may move a boundary

- **The creator**, directly in the Master Narrative: insert, delete, split, merge, reorder, move a passage, edit a heading. Always a normal Revision (`creator_edit`).
- **An AI operation, only as part of a defined operation that yields a Revision**: drafting the Master Narrative (outline, then scenes), screenplay conversion (segmentation), whole-narrative regeneration, revised-screenplay import. Each goes through the mapping of §4 and guards G1, G2, G5.
- **Never the AI inside** targeted rewrite (a selection crossing a boundary is applied per scene; the containers, their ids and the boundary are untouched; output containing a scene container fails G1), Treatment/Beat Sheet sync, shot drafting, Look and entity operations, or fact repair. The model may propose a scene break; it cannot enact one outside the operations above.
- Lock friction applies as for any Master Narrative edit ([ADR 0005](../adr/0005-locks-are-server-enforced-domain-state.md)): structural edits are edits, locked scenes need the edit-through confirmation with server-computed impact, and AI-applied structural changes to a locked scope are held as Options.

## 3. Homing: which scene owns a Shot

A Shot's parent Scene is a stored fact owned by the Shot (#55), changed only by a recorded **re-homing** Decision (append-only). A Shot also anchors to a narrative passage by block ids ([`STORY-DOCUMENTS.md`](STORY-DOCUMENTS.md) §8). Block ids survive move, split and merge, so the system can tell which scene a Shot's anchored text now sits in.

| Cause of the new head Revision | Shots whose anchored text now sits in another active scene |
|---|---|
| **Creator direct structural edit** (split, merge, move passage, restoring a Revision) | **Re-homed automatically**, as one Decision group with the edit: deterministic from ids and undoable. A whisper reports "3 shots follow their text to Scene 5 · Undo". Order inside the new scene follows the narrative order of anchors. |
| **AI or import operation** | Never auto-moved. Re-homing is part of the confirmed mapping (§4.4); otherwise the Shots stay and the difference is a to-reconcile item. |
| **Anchor lost** (anchored block retired by a rewrite) | The Shot stays in its scene and is marked by lineage (`input-retired`). Never guessed. |

Re-homing moves only the Shot's parent. Frames and Takes stay on their Shot. Captured inputs that depended on adjacency or text change legitimately mark the work possibly out of date; nothing is cleared or regenerated. Moving a Shot between scenes outside a structural edit is #55's affordance and uses the same Decision.

## 4. Revision mapping

### 4.1 When mapping runs

Mapping is needed whenever a new Master Narrative head is produced from *incoming structure that carries no ids*: **whole-narrative regeneration** and **revised-screenplay import (re-conversion)**. Creator direct edits and region operations already carry ids and need no mapping. Mapping is decided **before the Revision is committed**, because ids are permanent: a wrong identity merge cannot be repaired afterwards, only the work can be moved.

A revised screenplay **replaces the head with mapping**; it is not text-merged into the creator's edits. When the computed mapping would retire, split or merge scenes that already have production work, the import first offers **Duplicate into a new version** (recommended) or **Apply to this project** (Record 2 D52.2, closing section); everything below in §4 describes applying in place. The previous head stays as the prior Revision and is restorable. Verbatim rules are unchanged (dialogue and story verbatim as `imported` runs; AI additions separate).

### 4.2 Deterministic first, AI second, ambiguity to the creator

1. **Handles (regeneration).** The outline step receives each active scene as a handle (`[S12] heading, one line`) and outputs, per outline scene, either a handle it continues or `new`. Code checks every handle exists and is used at most once (G2, G5). This is a model proposal under the usual rule: models propose, code commits.
2. **Deterministic signals (import).** Code scores each old scene against each incoming segment from: identical imported text; identical dialogue lines in order (the strongest signal, because dialogue is verbatim); equal heading; and the longest consistent ordered alignment of scenes. **Position is a tiebreaker and a consistency check, never a source of identity.**
3. **Certainty classes.** *Exact* (incoming equals the old scene's imported text), *strong* (mutually unique best match with clear margin, order-consistent), *ambiguous* (tie, one-to-many, many-to-one, or competing candidates), *none*. Numeric thresholds are tunable spec-level values validated on the golden fixtures of §8.
4. **AI assist, only on what code left ambiguous.** One L call, inside the creator-triggered operation (M3), receives the ambiguous old scenes and incoming segments as handles and returns structured proposals (match, split, merge or none) with an evidence quote per claim. Code verifies ids and that each quote is an exact substring (G2). The result is a **proposal with evidence**; it never decides.

### 4.3 What is never decided silently

An **ambiguous** match is never auto-picked, by code or by model. A model's handle claim in regeneration is a proposal and falls under §4.4 whenever it touches a scene that has dependants. An old scene left unmatched is never deleted; it is retired.

### 4.4 What the creator confirms

The creator confirms one **mapping review** (a single list, not a dialog per scene) when, and only when, the mapping contains something the creator cannot already have intended:

1. an **ambiguous** or model-proposed match involving a scene that has dependants;
2. an old scene **with dependants** that the incoming structure would retire, split or merge;
3. a matched scene whose current text contains creator-written or `ai_edited` runs and whose incoming text would replace it (default **Keep current**, per-scene **Take incoming**; the other version stays in history either way; Record 2 D52.3, reversing the earlier default).

*Dependants* means anything that references the scene id besides the narrative itself: Shots, Look assignments, locks, anchors from Established Facts or entities. A scene with none never prompts, so a project with no production never sees a review.

For each item the creator chooses; no default is applied to ambiguity. The review can also be committed with items left **unmatched**: unmatched incoming scenes become new scenes and unmatched old scenes become retired with their work attached. The creator makes that choice explicitly by pressing Apply with the unresolved count visible; it is never applied silently. "Adopt work from a retired scene" (§5.1) remains available afterwards.

Not confirmed: exact and strong matches with no change of structure, pure inserts, and every creator direct edit. The review records one **Decision** (the mapping, the evidence and the creator's choices) tied to the Generation.

### 4.5 Revision-mapping semantics

| Edit | Ids | Production disposition | Marks (via lineage) | Creator confirms | Method |
|---|---|---|---|---|---|
| **Insert** a scene | New id; all others unchanged | None | Derived positions change (Looks by narrative position, [ADR 0002](../adr/0002-looks-and-carry-forward-derived-from-narrative-position.md)); adjacent-context captures: `narrative-changed` where captured | No | Deterministic (creator) |
| **Delete** a scene | Retired; id permanent | Shots, Frames, Takes, anchors stay attached to the retired Scene; out of batch scopes and default export | Dependants that captured it: `input-retired`. Look assignments anchored to it go inert, retained | Lock edit-through only | Deterministic (creator) |
| **Reorder** | Unchanged | None | Captured continuity context and derived Looks: `narrative-changed` where captured | No | Deterministic (creator) |
| **Split** | Upper keeps; lower new with `split_from` | Shots follow their anchored text (§3, automatic, undoable). Look assignments with a passage anchor in the lower part follow; scene-start assignments stay | `narrative-changed` on affected Shots | No | Deterministic (creator) |
| **Merge** | Earlier keeps; later retired with `merged_into` | Shots of the later scene re-homed into the survivor after the earlier scene's shots (automatic, undoable). Anchors to the later id redirect to the survivor at the former start of that passage | `narrative-changed` on re-homed Shots and their continuity context | No | Deterministic (creator) |
| **Rewrite** (selection, scene or region) | Container id kept; children by the STORY-DOCUMENTS §5 rule | Nothing moves | `narrative-changed` on Shots anchored to changed passages; `input-retired` if an anchor block was retired. No judgement of "substantial": any change to a captured passage marks, nothing else does | No | Splice (creator or AI) |
| **Whole-narrative regeneration** | Matched scenes keep ids; new scenes new; unmatched old retired | Shots stay with their scene id; none auto-moved | As above per matched scene; `input-retired` for retired | §4.4 | Handles proposed by AI, verified by code |
| **Imported revised screenplay** | As above | As above | Scenes whose incoming text equals their old imported text are left exactly as they are, including AI additions and creator edits, so a re-import that changes two scenes marks only those two | §4.4 | Deterministic signals; AI assist for ambiguity |
| **Removed or changed while production exists** | Removed: retired. Changed: id kept | All work stays attached and reachable (§5) | As above | By creator edit: no. By AI or import: §4.4 | Per cause |

## 5. Disposition of production work

### 5.1 Removed (retired) scenes

- Retirement is **derived** (no container in the head). The work is never touched, never marked deleted, never auto-regenerated, and never spends.
- **Whisper only** (M1): the Outline lists a collapsed, low-contrast group "Removed from Story (n)" holding retired scenes that have work. Retired scenes without work are reachable from narrative history. At the position in the Master Narrative where the scene used to be, a quiet note reads "Scene removed. 12 shots of work kept". No banner or modal. The review-all tray includes them.
- A retired Scene is **viewable and exportable** (Frames, Takes, history) and is excluded from batch scopes, Board runtime and the default export order. New generation inside a retired scene is not offered until it is brought back or its work is moved, so the creator never spends on work outside the film.
- **Bring back.** Restoring a narrative Revision reactivates the scene by id automatically. A direct "Bring back this scene" action appends a Revision that re-inserts a container with the **same id** and its last text from the Revision where it last appeared; the creator picks the position (default: the former slot).
- **Adopt work.** "Move this scene's work to Scene X" re-homes all its Shots into an active scene as one Decision group; creator-initiated, undoable, never automatic. They are placed after Scene X's existing shots, in their old order (as for merge). Frames and Takes stay on their Shots. Shot anchors are kept as recorded, never re-pointed or guessed onto Scene X's text: anchors to blocks retired with the scene do not resolve and are marked `input-retired` (the lost-anchor case of §3 and [`SHOT-MODEL.md`](SHOT-MODEL.md) §3.2). Re-anchoring an adopted Shot to Scene X's text is the creator's ordinary shot edit. This differs from Ad-hoc shots' "Move to scene", where the Shot had no anchor to begin with.

### 5.2 Split scenes

Shots follow their anchored text (§3). A Shot whose anchored text itself straddles the new boundary stays with the upper (id-keeping) scene and is marked; the creator can split the Shot (#55). Frames and Takes are untouched.

### 5.3 Merged scenes

Shots of both scenes live in the survivor in narrative order. The retired scene keeps `merged_into`, so old anchors, links and history resolve to the survivor (the same redirect pattern as entity merge). Both ids stay valid forever.

### 5.4 Incoming material with no scene

Text before the first heading, or any imported content segmentation cannot place, is reported (G5) and never dropped. Placement needs the creator once: join the neighbouring scene or become its own scene. No placement is guessed.

## 6. Interaction with lineage, locks and Looks

- **No new staleness reason.** Structure effects use existing reasons (`narrative-changed`, `input-retired`) and the existing Acknowledgements ([`LINEAGE-AND-STALENESS.md`](LINEAGE-AND-STALENESS.md) §3.1). Mapping never re-stamps a Basis; only the creator's reconcile does.
- **Locks.** A lock on a scene attaches to its id. Delete, split, merge, mapping retire and rewrite of a locked scene are edits to a locked scope: confirmation with impact; AI-applied changes are held as Options. Locks follow `merged_into`.
- **Looks and Facts.** Anchors to a retired scene are inert, not removed, and return on restore. Redirects follow `merged_into`.
- **Duplicate project.** Full duplicate: container ids remap with everything else. Duplicate without production (D52.2): no scene containers are carried; the new Master Narrative's scenes get new ids from the imported screenplay. How the source's scene-anchored Look assignments and Fact anchors carry into the new version is not yet decided.

## 7. Considered alternatives

| Alternative | Why rejected |
|---|---|
| Separate Scene row bound to a container block id | Two ids for one thing; split, merge and restore need a binding table kept in step. Restoring an older Revision would not reactivate a scene by itself. |
| Identity from heading or content hash | V1's slug and number failures: renaming or rewriting a scene becomes an identity change. |
| Positional identity | V1 D3: an insert re-points all later work. |
| AI picks the match silently | Violates "never silently auto-picked"; a wrong identity merge is irreversible. |
| Always ask for every mapping | Noise on every re-import; most matches are exact. |
| Three-way text merge of a revised screenplay into a creator-edited narrative | Edits creator text unrequested. Replace with mapping instead; old text stays in history. |

## 8. Invariants and fixtures the spec should test

Scene ids are never derived from text or position. Deleting a scene deletes nothing else. Restoring a narrative Revision reactivates retired scenes by id. A re-import in which only scene k changed marks only scene k's dependants. Reading or refreshing writes nothing. Insert at k, delete k and reorder (the V1 table, legacy 06 §8.3) leave every Shot with its original scene and text. Split then undo, and merge then undo, restore Shot parentage exactly. A mapping with an ambiguous item cannot be applied without a creator choice for that item. A targeted rewrite across a boundary leaves container ids and the boundary unchanged.

Golden fixtures: renamed headings; a scene split in the revision; two scenes merged; a reordered act; duplicate headings ("INT. KITCHEN - DAY" twice); a scene rewritten beyond recognition; text before the first heading.

## 9. Hand-offs

**Shot model (#55).** A Shot's parent is a Scene id (the container block id). Shot anchors reference block ids. Re-homing is a Decision with the rules of §3. Shot split and merge are resolved in [`SHOT-MODEL.md`](SHOT-MODEL.md) §5 and are independent of scene structure. Shots of retired scenes stay valid.

**Writing experience (#58).** Scene operations in the editor (insert, split at cursor, merge, move, delete) and their whispers; the mapping review as one surface; the "Removed from Story" group; Bring back and Adopt work; duration field presentation; in-app cut and paste must be a move. Quiet by default (M1).

**Navigation and Board (#60).** The Outline shows active scenes by derived number and the collapsed retired group; per-scene runtime from selected Takes; scene batch scopes exclude retired scenes.

**Entities (#53, closed).** Look assignments and Mentions anchor to Scene ids, redirect through `merged_into`, are inert when retired, and passage-refined anchors follow their blocks.

**Persistence and architecture (#72, #71).** A Scene is a projection over the head Revision's containers plus the retire and re-home Decisions; indices on block id and Shot parent; a mapping applies in one transaction with its Decision; scene structure events are derived from block lifecycle (`split_from`, `merged_into`).

**Verification (#76).** The invariants and fixtures of §8.

## Record 2 amendments (D52, P7, X5)

- **Normal iteration stays in the same project.** Rewriting or regenerating a scene, moving passages and targeted edits never push the creator to a new project; downstream work is preserved and flagged (R2).
- **Major revised-screenplay import recommends a duplicate; the creator chooses.** Trigger (computed): the incoming scene mapping would retire, split or merge scenes that already have production work; the threshold is a spec-level tunable. The import surface leads with two choices, each with impact counts: **Duplicate into a new version** (highlighted; the current project is untouched) or **Apply to this project** (downstream work may become possibly out of date; nothing deleted). The new version copies Input and source material, Interview and Facts, Treatment and Beat Sheet (as development history), World Definition, settings and other upstream material. It does not carry scenes, shot plans, shots, frames or takes; the screenplay becomes the basis of the new Master Narrative. The two projects show a quiet "made from" link. There is no cross-project adoption of production work in V2. Below the trigger, import applies in place through the mapping review.
- **Removed from Story** is the Outline group for retired scenes with work. It stays organized so the old scene and its shots, frames and takes are visible, with Bring back and Adopt work. It is distinct from **Ad-hoc shots** (SHOT-MODEL).
- **P7.** Shots re-home automatically only on the creator's own structural edits, with a subtle undoable notice (for example "3 shots moved to Scene 5 · Undo"); AI or import changes never move production work without confirmation in the mapping review.
