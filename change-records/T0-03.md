## Concurrency design

`commit` runs in `store.write`, which takes the per-Account `pg_advisory_xact_lock` before the callback; head, lock state and base are read only after that lock is held, and the append follows in the same transaction. Primary key `(object_id, sequence)` is the state-based backstop. No session-level locks.

## Write paths

Every history write is `history.commit` (project creation inserts the non-creative `project` row directly, as `project.state` is not history). `insertObject/appendRevision/insertAttempt` are called only from `history` (R1 by convention; no lint added: no settled requirement assigns an import-boundary lint to this ticket). Paste and role change are the only callers.

## Decisions

- Source Material is a `source-material` object whose Revisions hold `{text, role}`; role change is a new Revision (the text stays byte-identical).
- NeedsConfirmation/HeldAsOption trigger: a lock Decision. The `lock` table exists, empty, writable by no runtime role; tests insert as `owner` (Postgres) or via a MemoryStore seam. No lock product path built.
- `derive` returns no markers and an empty impact until capture edges exist.
- Text containing NUL or lone surrogates is `Refused invalid-body` (JSON/jsonb cannot carry them), never altered.
- The side line is the `attempt` table (PERSISTENCE §3: stale-base loser). `held` origin only for generation actors.
- Not built: `unit_head`, outbox events, idempotency receipts, `working_copy`, edit-session storage.

### Reading of the ID authority

PERSISTENCE-AND-MEDIA §3 says identifiers are "128-bit, time-ordered (UUIDv7-class for index locality), minted by the injected `Ids` port". The canonical specification names no variant. I took UUIDv7 as the variant, since the text names it as the class, and added `Ids.ordered()`. `ProjectId`, `ObjectId` and side-line Attempt ids are `z.uuidv7()` and are minted only by `ordered()`. Account, Creator, audit and Better Auth ids stay UUIDv4 from #98. Moving them is prior debt outside #100 because nothing in #100's behaviour depends on their ordering; it is not done here.

### Slices (question raised)

No document names Source Material's slices. LINEAGE §1 class 2 says content is immutable and the role is a descriptor, and §3 says the unit is what the consumer read, so I declared a single `content` slice (the text). If the owning authority wants the role as a slice, that is an additive slice, not a rewrite.

**2. API idempotency (STORY-DOCUMENTS §4; canonical A1).**
- Owner and contract: the client supplies an opaque key in the `Idempotency-Key` header (`idempotencyKeySchema`, 1 to 128 chars of `A-Za-z0-9._~-`, contract-owned); missing or malformed is `400 invalid-request`. `api` parses it; `workflows` applies it.
- Persistence: `accounts.idempotency (account_id, operation, key, fingerprint, result jsonb, created_at)`, primary key `(account_id, operation, key)`, forced RLS, composite account FK, append-only trigger, `SELECT, INSERT` to `app`. `operation` is a closed vocabulary (`IDEMPOTENT_OPERATIONS`) with a generated CHECK covered by D3. Key charset/length is a table CHECK.
- Fingerprint: sha256 of the canonical JSON `{operation, request}` where request is the logical fields (paste: project id, text; role edit: project id, object id, base, role). Headers and field order are not included.
- Transaction and concurrency: `once()` runs inside `store.write`, which already holds the per-Account transaction-scoped advisory lock. It reads the record, replays it (same fingerprint) or throws `IdempotencyKeyReused` (different fingerprint, mapped to `422 idempotency-key-reused`, rolled back, nothing executed), else runs the command and records `{fingerprint, result}` in the same transaction. A rolled-back write leaves no record; overlapping duplicates serialize on the lock, so the second replays. No session locks, no in-memory mutex.
- Replay returns the stored `CommitOutcome` (including `StaleBase` or `Refused`, which are also results of an executed action) without executing: no new object id, Revision, action group or stale Attempt.
- Relation to action group: the key identifies the caller's request; the action group is minted by the first execution only and is not used for replay.
- Covered: Source Material paste and role edit. Not covered: reads, project creation (not history), anything of #102.
- Evidence (real API and PostgreSQL, `t0-03.test.ts`): paste replay, edit replay (no extra Revision or Attempt), 6 overlapping duplicates (one object, one Revision, one record, equal responses), key reuse with different input (422, nothing executed), same key on another operation is a separate action, same key in two Accounts independent, different key from a stale base gives `StaleBase`. History conformance: a keyed record rolls back with a throwing transaction, is Account-scoped, and cannot be recorded twice (both Stores). D1, D3 (`idempotency_operation`), D4 and D5 updated for the table; G1 sends a fresh key per request.

**3. `sync` provenance.** `AI_CAUSES` now includes `sync` (STORY-DOCUMENTS §6.3: each sync is one Generation). `sync` with a creator actor or no id is `Refused missing-provenance`, leaving nothing; `sync` with the generation actor and an id applies. Evidence: conformance "a sync Revision is AI-made" on both Stores; removing `sync` from the set fails it.
