## Behaviour

- **Recovery request** (`POST /api/recovery/request`): always answers `202 {"status":"accepted"}`, same headers, whether or not the email has an Account. An existing verified email gets one stored SHA-256 token hash (replacing any earlier one) and one mail through `Mailer`. The mail is sent after the answer path is decided, and a delivery failure is reported to `onMailFailure`, never to the caller, so neither content nor outage reveals existence.
- **Recovery complete** (`POST /api/recovery/complete`): in one transaction under a row lock, checks expiry against the injected Clock, sets the password through Better Auth's own hash and `updatePassword`, deletes every session of that creator and consumes the token. Unknown, expired, used or superseded tokens, and common passwords, give the same `recovery-refused`. Concurrent use succeeds once.
- **Link shape**: the token is in the URL fragment so it is not sent to servers or logged by the creator-facing page's host.
- **Rate limits** (OPERATIONAL-BASELINE §2.3): sign-in, recovery and invitation redemption, per client address and per submitted email, fixed windows in `auth.rate_limit` (Postgres, no extra store), atomic `INSERT ... ON CONFLICT` increments. The email counter counts every submission whether or not the email exists, and the counter key is a hash. A refused attempt answers `429 rate-limited` with `Retry-After`, including with the correct password. Recovery completion is limited per address only (the token is the secret and is not an identifier). Limits and the recovery lifetime are injected configuration with no default, as the specification requires for rate limits and lifetimes. Tests use small synthetic values.
- **Client address**: `createApi` takes `clientAddress(request)` from the composition root, which must return the address its trusted edge reports. The library never reads `X-Forwarded-For`.

## Repair after verification of `af20d22`

The independent verifier found that recovery completion sampled the Clock before waiting for the `auth.recovery` row lock, so a link that expired during the wait was accepted (200, password changed, sessions ended). Root cause fixed in `completeRecovery`: expiry is now judged with the injected Clock sampled after `SELECT ... FOR UPDATE` returns, the same pattern as invitation redemption. The `at` input was removed from `Identity.completeRecovery`. Regression test: "refuses a recovery link that expires while its completion waits for the row lock" holds the row lock, confirms a real PostgreSQL lock wait, advances the Clock to expiry, releases, and asserts 403, existing session still valid, old password still works, new password refused. Negative control: with the repair reverted this test fails (200 instead of 403); with it, `pnpm check` passes (97 tests). The earlier FC11 label of the Mailer port was a metadata mistake and is corrected above. No other behaviour changed.

## Second repair, after verification of `e04adcc`

The verifier found that sign-in counted its email by parsing JSON, while Better Auth also accepts form-encoded bodies, so form requests skipped the per-email counter. Cause: the pre-forward step treated an unreadable email as "count the address only" and forwarded anyway. Fix in `api`: the API contract is JSON (every other route parses JSON only), so sign-in now answers `400 invalid-request` unless the content type is `application/json` and an email string was read; only then is it counted and forwarded. Rejected: parsing every encoding Better Auth supports, which would duplicate its parser. Regression test: "sign-in accepts JSON only..." exhausts the email's limit with JSON, shows the form-encoded request with the right password is refused without cookies, and that it creates no session and consumes no attempts. Also corrected: the Mailer source comment label and trailing whitespace in this record.

## Third repair, after verification of `c7762ef`

The verifier showed a sign-in with the old password, started while recovery was mid-transaction, creating a session that survived recovery. Confirmed cause: under READ COMMITTED recovery's `DELETE FROM auth.session` cannot see a session the concurrent sign-in inserts later, and that sign-in verified the still-committed old password. Fix: `Identity.serializeSignIn` holds a per-creator Postgres advisory lock (key from the normalized email) on its own connection for the whole Better Auth sign-in, and `completeRecovery` takes the same lock (transaction-scoped) after the recovery row lock and before sampling the Clock. A sign-in already in flight therefore commits its session before recovery deletes sessions; one that starts later waits, then sees the new password. Rejected: a credential generation on sessions, which needs a Better Auth schema change and a check inside the `Auth` adapter. **No Draft `Auth` contract changed**: the change is in the `accounts` `Identity` seam and the `api` sign-in route (the sign-in lock is taken after the rate-limit count). Not covered: a two-factor challenge started before recovery and completed after it; 2FA is required only for the operator and this ticket does not change that flow. Regression test: "a sign-in with the old password that overlaps recovery cannot leave a session behind" pauses recovery at its final statement with a test-held advisory lock after the password change and session deletion, confirms through `pg_stat_activity` that recovery and the overlapping sign-in are both blocked, releases, and asserts recovery 200, the overlapping sign-in 401 with no cookie, A's older sessions 401, B's session 200, no session rows for A, old password 401, new password 200. With the sign-in serialization removed the test fails. The JSON-only test now also proves rejected form requests consume no attempts (three rejected forms, then full JSON allowance). Deterministic evidence: `pnpm check` 8 files, 98 tests; `pnpm rules` 24; schema and vocabulary checks pass; no migration or schema change.

## Migration
