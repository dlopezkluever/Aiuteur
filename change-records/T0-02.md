## Recovery

Recovery uses Better Auth's own reset endpoints. Configuration sets `revokeSessionsOnPasswordReset`, so consuming the single-use link deletes every session of that user inside the same transaction that consumes the token. The link expires after 3,600 seconds. Better Auth returns the same response for an unknown email and sends mail only for a known one. The adapter sends mail in the background, so a known email answers without waiting for SMTP. That prevents an enumeration timing difference.

The new password must pass the same length floor and common-password list as an invitation password. A refused password does not consume the link.

## Abuse limits

Limits are counted in Postgres before Better Auth sees the request, in `auth.abuse_counter`. The bucket key is a SHA-256 hash of the limited dimension. No raw address or email is stored. Each attempt increments both the address dimension and the email dimension. A request is refused when either exceeds its maximum. The refusal does not depend on whether an Account exists, so known and unknown emails get identical responses while throttled.

| Route | Per email | Per client address |
|---|---|---|
| Sign-in | 5 per 15 minutes | 20 per 15 minutes |
| Recovery request | 3 per hour | 10 per hour |

These numbers are this ticket's choices. The spec leaves numeric tuning to the owning slice (#80 comment on `session lifetimes and rate limits`). Windows are fixed, so the bound is per window. The values are constants in `accounts`, not configuration.

## Mailer

`Mailer.send({to, subject, text})` rejects when the transport or the recipient refuses. Two adapters pass one conformance suite (`describeMailerConformance`):

- The fake, `FakeMailer`, in `testing/`. It records messages in memory, and `hold()` lets a test delay delivery.
- The SMTP adapter, `createSmtpMailer`, in `accounts/src/smtp-mailer.ts`, built on nodemailer. The test runs it against an in-process `smtp-server` that parses the received bytes with `mailparser`.

SMTP was chosen because any transactional-email service with SPF and DKIM for the sending domain offers it. The vendor stays configuration, as OPERATIONAL-BASELINE §2.3 requires. No production composition root is wired in this ticket.

## Decisions

- Recovery uses Better Auth's reset endpoints and session revocation, not a new recovery token table. The library already consumes the token and deletes sessions in one transaction. A parallel implementation would duplicate that.
- Abuse counters use Postgres with fixed windows, as OPERATIONAL-BASELINE §2.3 requires. A sliding window or an external store was rejected as extra machinery with no requirement behind it.
- Counting happens before lookup, which is what makes the refusal existence-independent.
- Sign-in attempts count every request, not only failed ones. A correct password is also throttled once the limit is reached, so guessing cannot continue behind a successful request.
- Better Auth's two-factor plugin already caps TOTP attempts and temporarily locks the account after repeated failures. This ticket did not add a second limit or test that cap.
- Better Auth's built-in rate limiter stays disabled. Two limiters would disagree on counts and windows.

## Raised

- **The emailed link has no landing route yet.** The link Better Auth builds is `…/api/auth/reset-password/<token>?callbackURL=…`. Only the POST reset route is forwarded, so opening the link returns 404 until a browser or landing flow exists. The brief's demo uses the token through POST. Owner: the browser recovery flow (T0-08 or a product decision). This is a blocking open question for real recovery.
- **Mail failures are silent.** Better Auth runs `sendResetPassword` in the background and logs failures through its disabled logger. A creator whose recovery mail fails gets no error and no alert. Owner: the `ErrorSink` and alert work.
- **Client address source.** The API takes `clientAddress` from the composition root. No production root exists yet. A forwarded header must not be trusted without a proxy policy. Tests use a test header.
- **Invitation redemption limits are not implemented.** OPERATIONAL-BASELINE §2.3 names redemption among the limited actions. The ticket's behaviour lists only sign-in and recovery, so this is left out. Decide whether it belongs here or in a later ticket.
- **Counter rows grow without a sweeper.** Each distinct email or address that attempts sign-in or recovery adds a row. Expired-window cleanup belongs to a later operations ticket.
- **Timing equality is not measured.** The suite proves the known-email response does not wait for delivery. It does not calibrate a timing class. T0-01 made the same choice.
- **Nothing is frozen.** All contracts stay Draft.
