## Decisions taken from repository authority

1. **Guards** (AI-map §3, §5, §8): G1 schema; G2 reference integrity (the Treatment compiles no handles, so a handle-like token cannot resolve: REJECTED); G3 verbatim; G4 splice; G7 provenance (computed from the attach plan: every run `ai_generated` by this Generation). G5, G6, G8, G9 are not this ticket.
2. **G3 (repaired).** The verbatim-constrained segments are the quoted spans of the creator's own source (curly, straight, guillemet, corner and single quotes; a single quote inside a word is an apostrophe), delimiters included. G3 requires each to appear byte-equal in the result, in source order and in the same count (AI-map §3: "byte-equal … in the same order and count"). The result is never scanned for quotation marks, so changing the quotation style, altering a line, omitting it, reordering or repeating it all fail the same way. No fuzzy matching. *Not implemented:* the AI-map §4.1 handle mechanism (the model emits `[D12]`, code restores the text). It needs the compiler to label source dialogue, which changes the Source Material layer and the scaffold (a prompt change that needs VC14 evidence, see the stop-line). The deterministic presence check gives the same guarantee on the output side without a prompt change; the handle form remains the owner design for VS1/VS2.
3. **One bounded repair, as run 2 of the same Generation (repaired).** A G1–G3 refusal settles Job run 1 (`succeeded`, run reason `repair:<guard>:<reason>`, draft call and verdict logged) and creates Job run 2 in the same transaction, claimed through the Scheduler port and dispatched by the same single path. Its Job id is the provider key (JOB-LIFECYCLE §4: a new run has a new key); there is no fabricated id. Its Rendered request is rebuilt deterministically from the stored draft call (`repairRequest`), carries its own Fit report (the added part counts against the prompt limit) and digest, goes through F3 with that digest and Fit, and is stored on the repair call with the response, verdict and reported cost. A repair that is refused, unconfirmed or fails still writes its call and its run (`billed` as the provider said), so no billed or maybe-billed exposure disappears. A second failure is REJECTED. The Generation's actual cost sums every call's reported quantities.
4. **HELD before repair (repaired).** The base is re-read before the repair decision. If it changed, there is no repair call: the result goes to the HELD path.
5. **HELD keeps the output as an Option (repaired).** A changed base settles the Generation `succeeded` with `held:G4:base-changed` and the paid output committed as a Treatment Option (actor `generation`, provenance G7), linked to the Generation. Options are never applied to a document, so nothing is applied. If the held proposal also failed a G1–G3 guard, the failing verdict stays on the call log and `choose` refuses that Option (`invariant-violated`): there is no "use anyway" for altered dialogue. A proposal G1 cannot parse has nothing to retain and is REJECTED.
6. **`spend.admit`** (FC10, BUSINESS §6.3): pure `admit({estimate, facts, now, caps, timeZone})`, run in `generation.create` under the Account write lock. A refusal returns before any insert. Order: ceiling (studio limit), per-action, daily, monthly creator caps. An unknown estimate is refused. Caps are an injected `Caps` with no default.
7. **Actual cost (repaired, BUSINESS §4.4).** `ActualCost` gains `computed` (additive; `reported` and `unknown` unchanged), produced when a run is known billed and the provider reported nothing, from the estimate's nominal quantities and the price entries. A settled reported or computed actual counts; a billed run without any actual counts its estimate; each `maybe`-billed run adds one estimate until reconciled (`SpendFact.maybeRuns`, from the run history).
8. **Account-local periods (repaired, BUSINESS §6.1, §9).** Day and month are the Account's local calendar day and month (`Intl`, IANA zone). The zone is `settings.timeZone` (optional, no default; no Settings UI). An Account with a limit configured and no timezone cannot be admitted: the creating transaction throws and creates nothing (500) rather than guess a zone. An Account configured as UTC uses UTC.
9. **Duplicate guard.** Layer 1 is #102's idempotency row keyed by action id. Layer 2: `input_fingerprint = sha256(canonicalJson({operation, project, target, Rendered request digest}))`; an unsettled Generation of the Account with it makes creation return `already-generating` (409) with that Generation's id.
10. **Migration 7 is an expand step (repaired).** `generation.input_fingerprint` is nullable with no default, so the previous image's Generation insert (no such column) still succeeds during a rolling deploy; `generation_call.rendered_request` is nullable. The new reader maps a null fingerprint to "none", which matches nothing. `generationReadSchema.inputFingerprint` is nullable.
11. Wire results added to `draftTreatmentResultSchema`: `cap-reached` (no Start), `studio-limit`, `price-unknown`, `already-generating` (409).

## Repair after verification FAIL of `bd9107f`: multi-run spend accounting

**Bug (found by the independent verifier).** The Generation's actual was built from all earlier calls' *reported* quantities plus the current run's; when the repair run (run 2) succeeded without reported usage, it was dropped (run 1's reports were non-empty), and when nothing at all was reported the "computed" fallback priced the Generation's *estimate* quantities, whose output amount is the request's maximum: an upper bound passed off as an actual. The settled actual was too low, and it feeds the next `spend.admit`. The spend unit tests passed because they supplied nominal quantities directly.

**Fix.** Each run is priced from its own facts (`spend.settleActual`, `spend.derivedQuantities`; `generation/dispatch.ts` `spent`):

- Runs in scope are those whose run-history row is `billed: yes` (the earlier calls plus the run settling). `no` contributes nothing. `maybe` contributes nothing to the actual and is counted once, as an estimate, by `SpendFact.maybeRuns` until reconciled, so there is no double counting.
- A run is priced by its **reported** quantities, else by quantities **derived from that run's own stored Rendered request and response**: exact quantities from the request, and for token-priced text the output the declared counter finds in the response, clamped to the request's bounds. The repair call row already stores its own Rendered request and response, so nothing new is persisted and there is no second ledger; run 1 is re-derived from the Generation's request and its call.
- Costs add, each run once. Form is `reported` when every run was reported, else `computed`. If a billed run's quantity cannot be known (no declared rule, a bound only the provider knows), the actual is `unknown` (billed yes), which the cap check counts at the Generation's estimate (conservative). The estimate is never recorded as a computed actual.

**Evidence** (`t0-06.test.ts`, "a Generation's actual cost covers every run once"; `spend/test/admit.test.ts`):

| Case | Result |
|---|---|
| Verifier scenario through the real path: run 1 reported, repair succeeds without usage; settled actual `computed` = run 1 reported + run 2 derived (expected computed in the test from the stored calls and price entries); a following request with cap = committed + upper − 1 is refused with `remainingMicros = upper − 1`, with cap = committed + upper it creates a Generation | pass; fails with the old behaviour planted |
| Reported + reported repair counts each run once | pass |
| Single run without usage: computed from its own request and answer | pass |
| Unconfirmed repair: actual = draft's reported cost, `maybeRuns = 1`, counted once each | pass |
| Unit: derivation within bounds, no output without a response, each run added once, `no`/`maybe`/unknown | pass |

Also corrected a comment in the compatibility test (the base call insert has no `rendered_request`; the base Generation insert has no `input_fingerprint`).

Gates: `pnpm check` 19 files, 288 tests; `pnpm rules` 24; fresh migration chain, `schema.ts --check`, `vocabulary.ts --check`; `git diff --check`. See the gate result in the PR handoff.

## Repair after verification FAIL of `a46e27c`: the settling run was not in the spend record

**Bug (found by the independent verifier).** A repair that failed with `billed: yes` and no reported usage vanished from committed spend. `failedRun` passed no current run to `spent`, and `spent` read only calls *before* the current run, so the settling run fell between history and aggregation: the settled actual held run 1 only. Including it alone was not enough: an uncomputable billed run makes the Generation actual `unknown`, and the cap check then substituted the original Generation's single estimate, losing run 1's known cost and understating a larger repair request. The same flaw applied to a maybe-billed repair, counted as `maybeRuns × original estimate`.

**Fix: each run records what it counts, once.** `generation_run.counted_micros` (migration 7, nullable, so the previous image still inserts runs) is written with the run, from that run's own facts (`spend.runCounted`, `spend.upperBoundMicros`; `dispatch.ts` `countedNow`):

- `billed: no`: 0.
- `billed: yes`: its reported quantities priced, else the quantities derived from its own Rendered request and answer, priced. If its quantity cannot be known (a failed run has no response, so its output is only the provider's to say), the run's own upper bound: its own request at the declared maximum, by the declared rule and price entries.
- `billed: maybe`: the run's own upper bound until reconciled.
- The settling run is included at every settle site (success, repair-trigger, REJECTED, failed or refused), computed from the `outgoing` request it actually sent, so it is never also read from history.

`spendFacts` returns the sum of a Generation's run counts (`countedMicros`, null if any run predates the column). `committed` is: the Generation's estimate while unsettled; else `countedMicros`; else, for legacy runs only, the actual or the estimate. The `maybeRuns` mechanism is removed. The Generation's `actual` is unchanged in meaning (an unavailable actual stays `unknown`; an upper bound is never recorded as a computed actual). The Generation and its runs remain the only spend record. (The staleness limitation that stood here was a verified blocker and is repaired in the next section.)

**Evidence** (`t0-06.test.ts`, 23 cases; `spend/test/admit.test.ts`, 16 cases):

| Case | Result |
|---|---|
| Real path: run 1 reported, repair fails `billed: yes` with no usage; `countedMicros` = run 1 reported + the repair request's own upper bound (derived in the test from the stored repair request and prices; larger than the original estimate); actual `unknown`; next request refused at cap = committed + U − 1 with `remainingMicros = U − 1`, admitted at committed + U; the test also asserts those boundaries differ from run-1-only and original-estimate-only totals | pass; fails with the failed run's count planted to 0 |
| Failed repair `billed: no` adds nothing beyond run 1 | pass |
| Unconfirmed (maybe) repair: actual = run 1 reported; `countedMicros` = run 1 + the repair's own upper bound | pass; fails with the count planted to 0 |
| Successful repair with missing usage: actual `computed`, run 1 + run 2 once; fully reported repair once each; single run missing usage `computed` | pass (unchanged) |
| Unit: run upper bound; `no`/`maybe`/`yes` counts; legacy facts without per-run counts | pass |

Not independently exercised: reported or computed actuals for a *failed* run (the failed provider result carries neither usage nor a response in the current contract; no provider contract was expanded).

## Repair after verification FAIL of `72d9a38`: stale-price widening of per-run exposure

**Bug (found by the independent verifier).** `upperBoundMicros` priced a run's conservative exposure (failed `billed: yes` with unavailable actual, and `billed: maybe`) at the raw declared prices, so a stale Published price (BUSINESS §4.3) was not widened. With prices 10 days old and a 1-day threshold the repair run persisted 33,099 micros where the widened bound was 36,409, understating committed spend and admitting a later request.

**Fix.** There is one stale-price algorithm, `spend.estimate`. `upperBoundMicros` now takes the same `EstimateInput` and returns the upper bound of the canonical estimate, so widening (and the unknown-price rule) is applied exactly once, by that code. `createDispatch` now receives the same `PricePolicy` as creation (`createWorkflows` passes its own; no new configuration, no default), with today's date from the injected clock. Boundary: `counted_micros` is final; nothing downstream widens again, and the Generation's estimate is not reused for a run. A known reported or derived actual is never widened. If the run's estimate is unknown (for example the price aged past the unknown threshold after admission), the run counts the Generation's admitted upper bound, an existing recorded figure, rather than an invented amount.

**Evidence** (`t0-06.test.ts`, 26 cases): stale policy (widen after 1 day, explicit test values): for a failed `billed: yes` and for a `billed: maybe` repair, `counted_micros` = run 1 reported + widen(repair request's own raw upper bound) (expected computed in the test from the stored repair request, the price table and the 10% allowance), larger than the raw bound and from a request materially larger than the original; a following request at cap = committed + next − 1 is refused (`remainingMicros = next − 1`) and at committed + next is admitted. Both fail with widening disabled in dispatch. Fresh prices are not widened; a reported actual under stale prices counts as reported. Earlier accounting cases are unchanged and green.
