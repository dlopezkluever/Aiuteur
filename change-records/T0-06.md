## Decisions taken from repository authority

1. **Guards** (AI-map §3, §5, §8): G1 schema, G2 reference integrity (the Treatment compiles no handles, so a handle-like token cannot resolve: REJECTED), G3 verbatim (every quoted dialogue line must equal a whole source dialogue line, in source order; exact comparison, no fuzzy matching), G4 splice (a new Option has an empty base, so the splice holds by construction; the base unit's content fingerprint is re-read in the settling transaction and a change is HELD), G7 (provenance computed from the attach plan; every run must be `ai_generated` by this Generation). G5, G6, G8, G9 are not part of this ticket.
2. **One bounded repair**: a G1–G3 failure gets exactly one more call (role `repair`, in the same Generation, F3 re-evaluated before it). Its Rendered request is the Generation's request plus one `repair` part from a versioned scaffold (`REPAIR_SCAFFOLD`) and is stored on the call. A second failure is REJECTED. A HELD result is never repaired.
3. **REJECTED** settles the Generation `failed` (`rejected:<guard>:<reason>`); both raw responses and their verdicts stay on the call log; no Option. **HELD** settles `succeeded` with no output (`held:G4:base-changed`); the raw response and the `held` verdict stay on the call log. HELD retention as a creator-choosable Option needs the Option/HELD UX (VS2); here it is retained on the Generation, never discarded or committed.
4. **FC6 Verdict** gains `pass: "held"`. `OperationSettler.validate` takes the Generation's ResolvedInputs; `current` and `base` are new (G4).
5. **`spend.admit`** (FC10, BUSINESS §6.3): `admit({estimate, facts, now, caps})`, pure. Committed spend = settled actual (`reported`), or the estimate's upper bound for unsettled, `maybe`-billed and unknown-actual Generations; `billed: no` counts nothing. Periods are UTC days/months (Accounts carry no timezone yet; spec-level). Order: ceiling first (studio limit; raising a creator cap cannot clear it), then per-action, daily, monthly creator caps. An unknown estimate has no upper bound and is refused. Caps are an injected `Caps` value with no default (`Execution.caps(scope)`); tests use explicit values. No ledger, balance or reservation. Where creator caps live per Account (the `accounts.caps` seam) is not built; the composition root supplies them.
6. **Admission runs in the creating transaction** (`generation.create`) under the Account's write lock, so concurrent creations serialise; a refusal returns before any insert, so no Generation, Job, capture or event exists. Scheduler admission (#102) is untouched.
7. **Duplicate guard**: layer 1 stays #102's idempotency row keyed by action id (replay returns the same Generation; now exercised concurrently). Layer 2: `input_fingerprint = sha256(canonicalJson({operation, project, target, Rendered request digest}))` stored on the Generation; if an unsettled Generation of the Account has it, creation returns `already-generating` (HTTP 409) with that Generation's id. "Generate another" is the creator's next action id once the first settles; the explicit override control is UX, not built.
8. Wire results added to `draftTreatmentResultSchema`: `cap-reached` (cap, remaining; no Start), `studio-limit` (plain, no content claim), `price-unknown`, `already-generating`. Refusals are 422; already-generating is 409.
