Alternatives for atomic redemption were compared locally. Calling the public signup endpoint then creating an Account needs compensation and exposes a partially created identity. Directly writing password hashes would duplicate Better Auth. The transaction-bound library instance keeps the operation atomic without either mechanism.

## Invitation and Account behavior

The operator is a verified email from the injected deployment allowlist plus a second factor verified on the current session. No role table grants this capability. Issuance writes the token hash, email, expiry and issuer, plus a content-free audit event in one transaction. Only the returned invitation contains the raw cryptographically generated token.

Redemption locks the invitation, then samples the injected Clock and checks expiry. This prevents a request queued behind another transaction from redeeming an invitation that expired while waiting. The transaction creates the verified Better Auth user, password credential, Aiuteur Account, version-1 default settings and subject mapping, then consumes the invitation. A duplicate email/id produces the same refusal as an invalid invitation. An unexpected database fault rolls everything back.

The invitation token proves control of the invited address. The API normalizes email case and accepts only the bound email. Passwords have a 12-character floor and 128-character ceiling. The local `@zxcvbn-ts/language-common` `passwords-common` dictionary is the selected commonly breached list, not a claim to contain every breached password.

Sign-in uses database-backed Better Auth sessions. Cookies are Secure, HttpOnly and SameSite=Lax. State-changing routes require the configured Origin and `X-Aiuteur-Command: 1`. Auth returns identity only. Each studio or operator request resolves Scope through `accounts.map_subject` before application work.

Lifetimes are injected configuration, not new product defaults. Synthetic tests use a 60-second invitation lifetime, 3,600-second idle lifetime and 86,400-second absolute session lifetime. Absolute age is checked by the Auth adapter. Better Auth owns its idle-expiry and refresh mechanics. Browser cookie renewal is not exercised by this API-only ticket.

The API demo is the integration test's real Hono Request/Response path, real Better Auth and migrated Postgres, with synthetic creators. It does not start an HTTP listener, send email, or deploy a web process. Initial synthetic invitations use the trusted identity adapter, never a public bootstrap endpoint. The operator test then enrolls TOTP, signs in with it, issues an invitation through the operator API and redeems that invitation.

## The migration chain is the source of truth

| Migration | Contents |
|---|---|
| `1-roles.sql` | SQL creation of owner, app, scheduler, identity, operator_read and backup. Owner has NOLOGIN. Runtime roles have no superuser, role creation, database creation, owner membership or RLS bypass. Backup is the sole deliberate bypass and has only read grants. Revoke public schema CREATE |
| `2-studio.sql` | Owner-owned Account and settings tables, forced RLS, default-deny transaction-local Account policies, composite settings key and tenant FK. Auth schema holds Better Auth core and TOTP tables, invitation, subject_map and audit_event |
| `3-audit-vocabulary.sql` | Generated CHECK for the only persisted closed vocabulary in this slice, `invitation.issued` |

The chain uses the installation bootstrap superuser only as migration tooling. No runtime connects with it. Cluster roles are reused when the chain builds another fresh database in the same disposable cluster. Runtime boot rejects an unsafe or incorrectly named app/identity login and indirect privileged membership.

Table classifications are explicit in the catalogue test. Account and settings are tenant tables. Better Auth, invitations, mapping and audit are auth tables outside tenant RLS, as PERSISTENCE §6.2 permits. The migration ledger is global reference data. There is no Project identity/history table yet.

The identity role cannot select tenant tables or enumerate subject_map. Its two allowlisted SECURITY DEFINER functions have fixed `pg_catalog` search paths. `map_subject` resolves one verified subject. `create_studio` validates that subject, sets the new Account context, and inserts only its initial Account/settings/mapping. There are no tenant views. Scheduler and operator_read have no table access until their later operations exist.

`schema.json` is generated from the migrated catalogue. `rows.generated.ts` is generated from that snapshot and remains adapter-private. Migrations become immutable after merge. A later vocabulary change needs a new generated expand migration, not a rewrite of migration 3. The current vocabulary generator creates/checks this first migration only.
