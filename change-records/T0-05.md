## Decisions taken (from repository authority; no creator input was needed)

1. **The text fast path claims its own Job** (RUNTIME §4.6): `execute` creates the Generation and Job in one transaction, then calls `jobs.claim(1, jobId)` through the Scheduler port and runs the single dispatch path in the request. No worker loop exists yet; a Job the fast path cannot claim stays durable and due.
2. **Idempotency is keyed by the Initiation's action id** (the request's `idempotency-key`, JOB-LIFECYCLE §4). A replay returns the Generation that already exists and sends nothing. A blocked fit or an unavailable selection is not stored, so a retry after the cause changes can create.
3. **Transaction boundaries** (JOB-LIFECYCLE §3, §11): (a) create: idempotency row, Generation with every trace field, capture edges through `history`, Job, `job.state_changed` event; (b) write-ahead intent: `queued → submitting`, before any provider call; (c) settle: call log, G1 validate, `history.commit` of the Option (actor `generation`, cause `ai_generation`), run history, settlement with the actual cost, the Job's terminal state and the `generation.settled` event. A rejected or failed result settles the same way without an Option.
4. **The F3 gate is one pure function over the closed, ordered `DISPATCH_GATE_CLAUSES`**: status, snapshot, credential, fit, inspector-digest, estimate, environment, authorised. `authorised` holds its reserved last position and refuses only voice work (`audio.transform`, `audio.speech`, `audio.voice`), which nothing can authorise before EI7. No spend admission (`spend.admit` is T0-06's). The estimate clause refuses only an unconfirmed Unknown estimate, and nothing confirms in T0-05.
5. **The #101 billed-quantity seam mattered and was resolved minimally**: `billedQuantity` on the adapter face returns `readonly BilledQuantity[]`, and `succeeded.reportedCost` is an array, so token text bills input and output separately. Media rules return one entry. `spend.actual(reported, entries, billed)` prices what the provider reported.
6. **Synchronous text** gets one new `SubmitResult` variant, `completed` (status inline). The fake text profile declares its run behaviour (idempotency `neither`, no webhook, maxRuntime 120 s, no cancellation, output retention `declared-none`, an error map). This gives the profile a new snapshot id; the VC2 golden judged it `stale` (fixture change, replay unchanged). It was regenerated with `--update`: Rendered request and digest unchanged (`sha256:9b573f…`), and the new id is appended to the golden's history.
7. **Choose is a Decision** (`type: choose`) through `history.decide`, creator only, refused for another project or kind, and gated by a lock like a commit. "Chosen" is derived: the project's latest choose Decision on a Treatment Option names it. Nothing is stored as a flag (D6).
8. **The Treatment Option kind is a block document**. A T0a Option holds paragraph blocks only, and its first Revision is all `ai_generated` runs naming the Generation. The `dialogue` block kind (speaker attribute, delivery and line fields) is in the shared block schema (EI4) but not admitted into a Treatment Option.
9. **Scheduler access** (RUNTIME §5): four SECURITY DEFINER functions `job_claim`, `job_extend`, `job_release` and `job_wake`, executable by the `scheduler` role only. They run as owner and see every Account's Job rows only while a transaction-local `aiuteur.claim` flag is set, through a second policy `scheduler_claim TO owner`. They return ids, states and lease tokens, never content. The `scheduler` role has no table privilege (D4 unchanged for it).

## Repair after verification FAIL of `527c8977b0ec2c51047dba8f960c51d7372aa825`

The independent verifier passed everything except one blocker: the FC5 Scheduler did not implement claim admission and fairness (RUNTIME §4.3). Both adapters claimed due Jobs by due time and Job id alone. There was no cap configuration, no provider or Account in-flight cap, no breaker check and no least-loaded ordering, so `claim(10)` over one Account's due Jobs leased all of them. The verifier's reading matches the authority:

- RUNTIME §4.3: "a due `queued` Job is claimable only if the provider's circuit breaker is not open (S7, a shared row), the provider's in-flight count (submitting, running, cancelling) is below its cap, and the Account's in-flight count is below its cap. Among claimable Jobs the order is least-loaded Account first, then oldest queued … Caps are configuration (S8, spec)."
- §4.6: local work never passes the breaker or these caps.
- §5.1: in-flight counts are not stored, and the claim counts Job rows inside its transaction.

Spend admission stays where §4.3 puts it, in the creating transaction (T0-06).

### Repair

- **FC5 Draft adjustments.**
  - `Admission { accountInFlight; providerInFlight: Record<provider, number> }` is injected into both adapters: `createPostgresScheduler(…, { admission })` and `MemoryStore.scheduler({ admission })`. It has no defaults, and a provider with no configured cap admits nothing (the spec invents no default).
  - `JobRow.provider` is the Offering's adapter, set by `generation.create` from the selected profile. It is null exactly for local work, enforced by a CHECK.
  - The port's `claim` doc now states the §4.3 rule. No port method changed.
- **Breaker.** A new operator-scoped table `operator.breaker (provider, open, opened_at, updated_at)` holds the "shared row" §4.3 and §5.1 name. It has no `account_id` and no content, and it is on PERSISTENCE §3's mutable-cell list. Only `backup` has SELECT. Its write path (`breaker_record`, `breaker_clear`, PERSISTENCE §6.5) belongs to S7 and is not built. The conformance seam writes it as the bootstrap role, as the lock seam does. The in-memory adapter keeps the same state behind `MemoryStore.setBreaker`.
- **Claim.** `accounts.job_claim` gains `account_cap` and `provider_caps` parameters. It runs under the same transaction-scoped advisory lock, in two steps:
  1. **Ungated work.** Due work that admission does not gate (Jobs already in flight whose lease or deadline is due, and local work) is leased first, oldest due first, as before.
  2. **Admission.** One Job per iteration, over exact counts. A due `queued` provider Job is eligible when all three hold:
     - its provider has no open breaker row;
     - the provider's in-flight count is below its cap;
     - its Account's in-flight count is below the Account cap.

     Among eligible Jobs, the order is the Account's in-flight count, then the Job's `created_at`, then the Job id. Each lease raises that Account's count before the next pick, so picks alternate across Accounts.

  "In flight" means a provider Job that is `submitting`, `running` or `cancelling`, or `queued` under a live lease (claimed and about to submit). Without the last case a second claimer could take a slot the first had already leased. The text fast path's `claim(1, jobId)` passes the same admission. The in-memory adapter implements the same two steps over the same definition.
- Migration 6 is amended in place, not followed by a migration 7, because it has never been merged or applied outside disposable databases. `schema.json` and `rows.generated.ts` were regenerated, and `schemaCatalogue` now also snapshots the `operator` schema's grants.

### Conformance added (shared suite, run on both adapters)

| Case | Asserts |
|---|---|
| §4.3 provider cap | With a cap of 2 and three concurrent `claim(10)` calls over four due Jobs in two Accounts, exactly 2 are leased. ## Repair after verification FAIL of `0eed4dc3110659d2fa3e90398faa84f87e459055`

The second independent verifier passed the §4.3 admission repair and everything else, with two blocking Scheduler defects.

1. **Deadline-expired queued work was admission-gated.** A `queued` provider Job past its admission deadline was still subject to the caps and the breaker. With capacity full, `claim` returned nothing and the Job never timed out. The authority:
   - RUNTIME §4.2's tick: "past the state deadline, fail with the deadline's reason … a Job past its deadline is due, so the same claim finds it".
   - JOB-LIFECYCLE §2: `queued` has an "Admission deadline 60 min → failed (`queue_timeout`, unbilled, transient)".
   - Admission (§4.3) gates submission, not the timeout.
2. **Separate in-memory adapters over one `MemoryStore` could over-admit.** Each adapter had its own claim lock, so two adapters could read the same pre-claim counts and each lease a Job against a cap of 1. Postgres was already correct, because one advisory lock covers every claimer.

### Repair

- **Claim, both adapters.** A `queued` provider Job whose `deadline_at` has passed is ungated work, leased in the first step with in-flight and local Jobs, oldest due first, whatever the caps or breaker. The admission step excludes such Jobs. Ordinary queued Jobs are still admitted exactly as before. Postgres: two predicates in `accounts.job_claim` (migration 6 amended in place; `schema.json` regenerated). Memory: the same predicate in `gated`.
- **Tick, the single dispatch path.** Dispatch acts on the state read at claim. In its first transaction, a `queued` Job past its deadline is settled `failed` (`transient-unbilled`, billed `no`, reason `queue_timeout`) through the existing settle path: run history, settlement and the `generation.settled` event. It never moves to `submitting`, and nothing is sent. No other daemon or subsystem was added.
- **In-memory claim lock.** The lock moved from the adapter closure to a private `MemoryStore` field, so every Scheduler adapter over one store serialises its claims on it, as the advisory lock does in Postgres.
