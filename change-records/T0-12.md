## What was built

- **`media`** (MODULE §3.4): `keys` (the only key builder, R17), `put(wtx, scope, project, {kind: "upload", uploadId})` and `access(rtx, scope, ref, purpose)`, plus `upload(rtx, scope, project)` for the signed staging PUT. `put` reads the staging object `a/<account>/p/<project>/t/<upload>/0`, refuses `upload-missing`, `empty`, `too-large` (cap from the composition root), `undecodable` (ffprobe for one still stream, then a full ffmpeg decode) and `type-mismatch` (probed type differs from the stored content type), hashes with SHA-256, copies server-side to `…/m/<hash>`, deletes staging, and inserts the Media row in the caller's transaction (reusing it when the project already has the hash). `access` reads the row under the Scope and signs the stored key, with `response-content-type` from the row and `Cache-Control: private` (and an attachment disposition for `download`); a ref the Scope cannot see answers null.
- **FC5 `BlobStore` port** (`store`): `put`, `head`, `get`, `copy`, `delete`, `sign`, every call taking a Scope. Each adapter refuses a key outside `a/<the Scope's Account>/` (or one with an empty, `.` or `..` segment) before touching the store, and `delete` refuses anything not under `t/`, `r/` or `x/` (R16). `MediaRef` is `{ projectId, hash }`.
- **R2 adapter** (`media/src/r2.ts`): plain S3 SigV4 (region `auto`, path style) through `aws4fetch`, no vendor SDK; presigned GET and PUT with `X-Amz-Expires`.
- **Fake BlobStore** (`testing/src/fake-blob-store.ts`): in memory, with a loopback HTTP server so signed URLs are real; the HMAC covers method, key, expiry and response headers; CORS for the browser's PUT.
- **Persistence** (migration `7-media.sql`, expand only): `accounts.media` (tenant, forced RLS, append-only trigger, `SELECT, INSERT` for `app`), primary key `(account, project, hash)`, and `CHECK (key = 'a/'||account||'/p/'||project||'/m/'||hash)`, so a row cannot name another Account's or project's object. `attempt.media_hash` with a composite foreign key to `media` of the same Account and project, and `CHECK ((origin = 'upload') = (media_hash IS NOT NULL))`. Merged migrations 5 and 6 are byte-identical; their generated blocks now take the prefix of the grown vocabularies, and 7 replaces the constraints with the whole set (the pattern 6 already used).
- **`history.upload`** (FC3, additive): appends an `upload` Attempt to an object's Slot after checking Scope, project, kind, that the Media exists in that project, and the lock (NeedsConfirmation without an edit session).
- **`world`**: the `character` kind (`{ name }`, slice `identity`) and `readCharacter`. The reference a Character shows is its latest upload Attempt.
- **`production`**: the `shot` kind (`{ action, presence: [{ entity, look: "base" }] }`, slices `action` and `presence`, invariant: an entity once), `presenceResolves` (each entity must be a Character of the same project under the Scope) and `readShot` (names resolved when read; no copy stored).
- **Use cases and API**: ten routes, all `access: "scope"`, each with a `ROUTE_RESPONSES` entry. `POST …/uploads`, `GET|POST …/characters`, `GET …/characters/:id`, `POST …/characters/:id/reference`, `GET …/characters/:id/reference/view` (answers `Cache-Control: no-store`), `GET|POST …/shots`, `GET …/shots/:id`, `POST …/shots/:id/presence` (with `base`). The reference attach runs `put` and `history.upload` in one transaction keyed by the idempotency key; a refused subject touches no bytes.
- **Client**: a project nav (Input · World · Shots) and two screens. World: add a Character, upload a reference through the signed PUT, show the image from a freshly minted view link (re-minted once if the image fails to load) with the frozen facts. Shots: make a Shot with an action and Presence checkboxes; change Presence on the read Revision; a StaleBase shows a notice, the kept-aside line and the server's state.

## Decisions taken

1. **The reference a Character shows is its newest upload Attempt.** ENTITIES §2 has one active Attempt per Slot; T0 has one way to fill the Slot (upload), and choosing among Attempts is VS5's. No Slot-choice Decision type was added.
2. **A hand-made T0 Shot is an ad-hoc Shot** (Record 2 X5): no Scene, so no derived Presence; its Presence is stored as explicit adds with Look `base` (the only Look until VS5). VS6 adds Scenes and derivation on the same kind.
3. **`media.put` runs inside the write transaction that adds the referrer.** The account lock is held during the blob copy and the probe. This makes a replayed attach return the first result and keeps "committed Media always has a referrer" without a separate reconciliation. If a later profile shows lock contention, the IO can move ahead of the transaction as PERSISTENCE §7.2 draws it.
4. **The probe runs in `web` for T0-12** (an upload arrives on a request). RUNTIME §4 puts `media.put` for provider outputs in the worker; T0-13 brings that path.
5. **R16 is an import-boundary rule plus a port guard.** Only `media`, `testing/`, `store` (which defines the port), tests and composition roots may import `BlobStore`, `createR2BlobStore`, `FakeBlobStore` or `deletableKey`; every adapter's `delete` refuses `m/`. `media.purgeProject` does not exist yet (purge is "built later", PERSISTENCE §9.2), so nothing deletes committed Media.
6. **The R2 adapter's conformance runs against a real S3-protocol server**, VersityGW v1.10.0 (posix backend), spawned by the suite from `S3_GATEWAY_BIN`. The pipeline installs it pinned and checksum-verified. A missing binary fails the suite. This proves SigV4 signing, presigned GET/PUT, expiry, copy and the key guard over HTTP; it is not R2 itself (see Raised).
7. **The upload request body is empty.** The type is the PUT's `content-type`, and verification decodes the bytes against it.

## Raised

- **What "another Account's signed link is refused" can mean.** A presigned URL is a bearer credential by S3 design. A link that A copies to someone out of band works for whoever holds it until it expires (PERSISTENCE §7.3 chose short lifetimes and never logging). What is proven here: B cannot obtain a link to A's Media, cannot turn its own link into one for A's key, and cannot guess a hash-named key. If the intent is that a link fails for any session but A's, that needs a proxied, cookie-checked media route, which is a design change to PERSISTENCE §7.3 and §13 P5 and not this ticket's work.
- The R2 adapter is proven against an S3-protocol server, not R2. The live R2 check (cross-Account signed-link refusal on staging) is T0-15's per #112. It needs the bucket from T0-10. The production composition root does not exist yet, so nothing wires the R2 adapter.
- Signed-URL lifetimes (view 1 h, download 5 min, upload 10 min) and the 10 MB upload cap are composition-root values, set in the CI root and tests; PERSISTENCE §14 leaves them spec-level.
- The bucket lifecycle rule for `t/` and the `m/` retention lock are operational (T0-10 / before the first non-owner invitation) and not configured here.
