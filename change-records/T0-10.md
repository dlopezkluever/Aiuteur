## Decisions taken

1. **No Sentry SDK.** The adapter posts the envelope itself. Smaller surface, no transitive auto-instrumentation to turn off, and the scrubber is the only producer of event content. If the owner wants the SDK, it replaces only `adapters/hosted.ts`.
2. **No message in error events.** The baseline allows "stack frames" and bans user strings and provider text. An error message is free text that can carry a prompt, so none is sent; class + code + frames + ids is enough to group.
3. **Runtime field guard besides the type.** Callers that bypass the type still cannot log free text: a key outside the set, or a value that is not id-, slug- or count-shaped, is dropped and counted.
4. **Release tagging.** Every log line and event carries `RELEASE_DIGEST`, which `deploy.sh` sets from the digest it deployed. `/healthz/deep` reports it.
5. **The deploy script, not the workflow, owns the mechanism.** The workflow ships the commit's deploy files and calls the script, so the same code runs by hand and in CI, and the stub-`docker` suite tests the same file the host runs.
6. **Fail toward the prior digest.** A post-swap smoke failure restores the prior digest inside the script and still fails the run. The compat smoke failing stops before the swap.
7. **Postgres trust auth inside the compose network.** Migration `1-roles.sql` creates the runtime roles without passwords (as the CI service does). The container publishes no port. Per-role passwords are a persistence-lane change and are raised below.
8. **Staging runs the fake provider.** `syntheticCatalogue` + `FakeTransport`, as R19 allows for staging; the production root that refuses fakes is not wired. The staging smoke covers deep health and the unauthenticated refusal. Sign-in and a fake-provider Job end to end (OPERATIONAL-BASELINE §4.2) need a staging smoke Account, which the owner has not provisioned; they join `runSmoke` with it.
9. **Worker does not claim Jobs yet.** Step executors belong to the tickets that build them (RT6: a stopped worker costs liveness only). It proves database reachability and drives the heartbeat.
10. **R2.** Settings are parsed and validated (account id, bucket, keys); the BlobStore adapter that uses them belongs to the media tickets.
