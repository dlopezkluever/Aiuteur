# 04 Creative State & Continuity

> Scope: how context, earlier decisions, and asset/visual state persist and flow from global to scene to shot to frame, and how continuity is carried, checked, and repaired. Legacy product thinking, not a description of current behavior. Legend: see 00-README.

## Persistent context: global vs local

Phase A (Stages 1–5) produces global truth; Phase B (Stages 6–12) runs one scene at a time and adds only scene-local specificity on top of it.

- **WD-IDEA-CONT-001** [impl] Context is split in two. Global context is always available and holds project-wide truth: target length, genre, tone, chosen writing and visual style capsules, the beat sheet, the master script summary, and locked master assets with their descriptions. Local context exists only while a scene is active: that scene's script excerpt, its shot list, its scene asset instances, and the previous scene's end state (asset states and final frame). Narrative structure (beat sheet and script, Stages 3-4) sits between the two. Stages 1-5 establish the global truth as immutable by default, not absolutely: a locked visual style can still change later with a warning about downstream impact, and a late change in production creates a branch (WD-IDEA-ASSET-026, WD-IDEA-CONT-034). Stages 6-12 add only scene-local specificity on top of it, so global changes can invalidate local work. Related: the invalidation scopes that realize this inheritance are WD-IDEA-UX-044 (the layer where a change happens) and WD-IDEA-UX-045 (global, local scene, and continuity break). ‹src: project-overview, development-progress, AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-002** [idea] No Phase B AI call includes the script of non-active scenes. This prevents drift, hallucination, and context overflow. ‹src: project-overview›
- **WD-IDEA-CONT-003** [idea] When master assets are locked at the end of Stage 5, the system assembles a global context package. It contains the beat sheet; the master script broken into scenes (each with slug, content and estimated duration); the visual style lock (which capsule, and when it was locked); every master asset (name, type, master description and reference image); the project parameters (target length range, content rating, genres, tonal guidance); and branch metadata (branch name, parent branch, and the stage it branched at). ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-004** [idea] Every Phase B AI step receives the same global context package, which stays unchanged throughout Phase B production. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-005** [idea] The global context package names its branch, so every AI step knows which creative timeline it is working in (see 10). ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-006** [planned, impl] Global context should carry the full asset manifest, visual style locks and constraints, and project-level continuity rules. ‹src: MVP-tasklist-v1.1, global-vs-local-context-BIG, master-mvp-tasklist›
- **WD-IDEA-CONT-007** [planned, impl] Local scene context should come from the stored scene-asset map rather than real-time extraction. It holds the scene's dependencies, the relevant asset inheritance chains, and the prior scene's end state. ‹src: MVP-tasklist-v1.1, global-vs-local-context-BIG, master-mvp-tasklist›
- **WD-IDEA-CONT-008** [impl, planned] Each scene records which characters, locations, and props it depends on. The scene dependency maps drive the scene hub's scene info (Stage 6) and the Stage 8 auto-suggestions. AI relevance detection remains available as a separate Detect with AI action (WD-IDEA-ASSET-159); whether suggestions rely on the map alone is an open alternative (WD-IDEA-ASSET-162, WD-IDEA-ASSET-163). Extraction is conceived to record these dependencies automatically. Missing assets can still be added manually. ‹src: development-progress, master-mvp-tasklist, injecting-org-tickets-into-plan›
- **WD-IDEA-CONT-009** [idea] Dependency rule: speaking characters must be present in the scene. Off-screen (O.S.) characters are also present in the scene, but not on camera. ‹src: tiptap-json-extraction-guide›
- **WD-IDEA-CONT-010** [impl, planned] When context must be trimmed, recent asset states take priority over distant history, and context size is monitored. ‹src: master-mvp-tasklist, MVP-tasklist-v1.1, missing_todos-not-sure›
- **WD-IDEA-CONT-011** [idea, impl] Context assembly is one centralized system, not logic scattered across stages. It automatically assembles and injects the right global or local context before every AI call, so the user never has to paste context by hand. This is the implementation side of the explicit, typed, versioned per-step context package in WD-IDEA-PHIL-045 and of the unchanged global package in WD-IDEA-CONT-004. ‹src: missing_todos-not-sure, development-progress›
- **WD-IDEA-CONT-012** [impl] When several assets get story-informed suggestions at once, the scene's story context is assembled once and shared across all selected assets, so their suggestions stay consistent with each other. Bulk inference is cost-aware: story context is fetched once per scene and reused, and small sets of assets are batched into a single AI call. ‹src: Infer-from-Story, 3.7-phase-2-story-context-updates, 3.7-threads›

### What each AI step sees

- **WD-IDEA-CONT-013** [idea] Beat extraction sees the selected treatment, the target length, the genre, the tonal guidance and the writing style capsule. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-014** [idea] Script generation sees the beat sheet, content rating, genre, tonal guidance and writing style capsule. It does not see the treatment prose directly. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-015** [impl] Phase B runs per scene. When the user selects Scene N in Stage 6, shot list generation receives the global context, Scene N's script content (and the beats it covers), and Scene N-1's end state as local context. The previous-scene end-state input is the mechanism in WD-IDEA-CONT-073, where shot-list generation uses the end frame and character positions so the next scene's first shot connects. ‹src: AI-agent-registry-context-flow-architecture, system-prompts-inventory›
- **WD-IDEA-CONT-016** [impl] Scene asset relevance acts as an "asset continuity manager." It sees the global context, the current shot list, and the previous scene's asset instances (their scene-specific description overrides, status tags and end-state summary), and decides which master assets appear in the scene. ‹src: AI-agent-registry-context-flow-architecture, system-prompts-inventory›
- **WD-IDEA-CONT-017** [idea] The scene visual-state step sees the master description, the previous scene's description (if any), the user's current-scene modifications, the global context, and the visual style capsule. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-018** [idea] The frame prompt step sees the global context, the shot, the scene's asset instances (with their overrides and status tags), the frame type (start or end), a reference to the previous frame, and the visual style capsule. ‹src: AI-agent-registry-context-flow-architecture›

## Inheritance contract

Authority flows one way: global intent, then narrative structure, then scene and shot specialization, then media realization. Later layers may narrow earlier ones but never contradict them.

- **WD-IDEA-CONT-019** [idea] Context always flows downstream. A downstream stage never changes an upstream stage, and a stage can never inherit from itself or from a later stage. ‹src: inheritance_contract, database-schema-state-transition-matrix›
- **WD-IDEA-CONT-020** [idea] Context sent to the model is built from layers ranked by priority, highest to lowest: local overrides; scene or character context; narrative structure context; global intent context; system constraints (hard limits). ‹src: inheritance_contract›
- **WD-IDEA-CONT-021** [idea] Prompts are assembled in a fixed order: system constraints, global intent, narrative context, scene and character context, local overrides, then selected style capsules. The result is frozen as an immutable snapshot. ‹src: inheritance_contract, tech-stack›
- **WD-IDEA-CONT-022** [idea] Every override must be explicit, limited to specific fields, and logged. An override never silently erases global intent. ‹src: inheritance_contract, database-schema-state-transition-matrix›
- **WD-IDEA-CONT-023** [idea] Allowed local overrides: visual emphasis, camera framing, momentary pacing, and shot-level verbosity. ‹src: inheritance_contract›
- **WD-IDEA-CONT-024** [idea] Forbidden overrides: genre, core tone, narrative thesis, and style locks. Attempts are rejected or flagged. ‹src: inheritance_contract›
- **WD-IDEA-CONT-025** [idea] Narrative-structure stages inherit all global intent. They may refine the global tone but never contradict it. ‹src: inheritance_contract›
- **WD-IDEA-CONT-026** [idea] Scene and shot stages inherit strongly from the global and narrative layers. They may override only local emphasis, never tone, genre, or style locks. ‹src: inheritance_contract›
- **WD-IDEA-CONT-027** [idea] Media-realization stages have no creative authority and are purely consumptive. A defect in the media is traced upstream and fixed there, never patched at the media stage. ‹src: inheritance_contract, database-schema-state-transition-matrix›
- **WD-IDEA-CONT-028** [idea] Attempted violations (forbidden override, authority escalation, style-lock violation, tone violation) are kept as permanent records of creative drift. Recording them does not block the work. ‹src: database-schema-state-transition-matrix›
- **WD-IDEA-CONT-029** [impl] Auditability: every generation records what it inherited, what it overrode (as diffs), which style capsules and versions it applied, its parent stages, its prompt versions, which retrieved reference documents it drew on (beats, script, image keys, frame prompts, scene asset states), and an observability trace, so generations can be audited and compared. Every artifact records what it was derived from, so its full lineage can always be traced. ‹src: inheritance_contract, database-schema-state-transition-matrix, development-progress›
- **WD-IDEA-CONT-030** [idea] Diagnosis path when output breaks a constraint: identify the violating field, trace the inheritance chain upstream, inspect context relevance, then adjust the prompt or the override rules. ‹src: inheritance_contract›
- **WD-IDEA-CONT-031** [idea] The inheritance rules stay fixed even when the orchestration engine, media providers, or style-management system change. ‹src: inheritance_contract›
- **WD-IDEA-CONT-032** [idea] Asset context flows global to local and then to scene instances: master assets first, then per-scene asset instances, then continuity tags. ‹src: architecture-and-rules, database-schema-state-transition-matrix›

### Style inheritance

- **WD-IDEA-CONT-033** [idea] Each style capsule application is explicitly scoped: global-only, narrative-only, scene-only, asset-specific, or combined with inheritance. ‹src: inheritance_contract, architecture-and-rules, database-schema-state-transition-matrix›
- **WD-IDEA-CONT-034** [impl] Changing a locked visual style shows a warning and offers a choice: mark existing asset images as outdated, or clear them. Marking them outdated sets a "style outdated" flag on each asset, and the user then triggers regeneration to match the new style. ‹src: current-app-user-flow, planning-wif-lawrence›
- **WD-IDEA-CONT-035** [idea] Lighting continuity: standardize 2–3 lighting and color descriptors across all frame prompts in a sequence so lighting does not shift between clips. ‹src: Frame_Video_Prompt_Format_Guide›

## Earlier decisions as durable context

- **WD-IDEA-CONT-037** [planned] Conceived: clarification answers become durable "established facts" rather than one-off inputs. A branch-scoped ledger records each question, the options offered, the chosen answer, whether the user or the AI resolved it, the subject entity (character, location, prop, style or structure), and which sources conflicted. AI-inferred resolutions are recorded the same way for audit. Recorded answers are re-read on every call and injected into later generations as established facts (WD-IDEA-CONT-038). The ledger's record of conflicting sources and AI-inferred resolutions is the intake-side behaviour in WD-IDEA-INPUT-123 to WD-IDEA-INPUT-125. ‹src: streamline-master-plan-8-1, streamline-plan-critique-8-1, streamlined-input-process-consolidated, streamline-implementation-spec-8-3›
- **WD-IDEA-CONT-038** [planned] Conceived: established facts are re-injected into every later Stage 2-5 generation as "ESTABLISHED FACTS (do not contradict)" and re-read on every call. As a result, even a from-scratch regeneration months later cannot drift from an earlier answer. ‹src: streamline-plan-critique-8-1, streamline-implementation-spec-8-3›

## Asset state: separate layers

Legacy docs keep an asset's look in distinct layers with different owners and lifetimes: canonical identity (master), scene appearance including wardrobe (per-scene description override), condition (status tags such as mud or blood), in-scene transformation, and the frame-moment expression, posture, and position.

- **WD-IDEA-CONT-042** [alt, impl] Canonical identity: each character has a consistency block (name/role, age, ethnicity, gender, hair, eye color, facial features, build, clothing, accessories, skin details) reused word for word in every frame prompt where the character appears. It is copied verbatim from the approved asset description, which is its single source; free-form per-shot wording was considered and rejected because it causes identity drift. Define-once-reference-many by name or alias is the considered alternative (WD-IDEA-ASSET-218). ‹src: Frame_Video_Prompt_Format_Guide›
- **WD-IDEA-CONT-043** [idea] A frame captures a frame-specific emotional expression and a static posture "frozen in this moment," kept separate from the character's canonical identity description. The frame-level expression and posture rule is written as a prompt standard in WD-IDEA-GEN-042 (posture, gesture, specific facial expression, gaze, physical state markers). ‹src: Frame_Video_Prompt_Format_Guide›
- **WD-IDEA-CONT-044** [idea] Wardrobe lock: a character's clothing and accessories stay identical across shots unless the story motivates a change. ‹src: Frame_Video_Prompt_Format_Guide›
- **WD-IDEA-CONT-045** [idea, impl] Scene appearance override: a scene-specific edit to an inherited asset (mud on the coat, a new hairstyle) applies to that scene only and saves a new scene instance (e.g. "John Doe (Scene N+1 - Muddy)") with an audit trail. The master stays untouched. The instance's image is regenerated only if its description changed; otherwise it inherits the project version. ‹src: project-overview, architecture-and-rules, development-progress›
- **WD-IDEA-CONT-046** [impl] Effective description precedence: the scene override comes first, then the description inherited from the prior scene, then the master description. Legacy docs describe location views as project-level only, shared by every scene instance of the location (WD-IDEA-LOC-245); per-scene location variants remain alternatives (WD-IDEA-LOC-248 to WD-IDEA-LOC-251). ‹src: 3.7-phase-0-investigation-findings, 3.7-phase-2-story-context-updates, jump-a-gun-discrepancies, architecture-and-rules›
- **WD-IDEA-CONT-047** [idea, impl] Condition (status) tags record temporary visible physical state of an asset in a scene, such as wet, bloody, muddy, torn wardrobe, torn shirt, or locked. They come from shot outcomes during production, or the user picks them from a keyboard-navigable dropdown. Each asset instance has a carry-forward toggle, on by default, that decides whether its tags persist into the next scene. A scene visual state therefore yields both a description override and status tags. ‹src: project-overview, architecture-and-rules, AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-048** [idea] Status tags can be applied only once the scene's shot list is ready, after Stage 7. ‹src: database-schema-state-transition-matrix›
- **WD-IDEA-CONT-049** [impl, planned, voice] Conditions must visibly reach the images. Status tags are appended as visual modifiers when scene-instance images are generated, and frame prompts describe the visual conditions of characters, props, and settings in detail, including damage or dirt. Frame prompt subject appearance comes from each asset's scene-specific effective description rather than only the master description, with status tags as condition modifiers. The scene-instance image recipe is: master reference as identity anchor, effective description as the prompt subject, status tags as visual modifiers that must visibly register, and the visual style capsule for aesthetic. ‹src: 3.7-phase-0-investigation, 3.8-phase3-structured-prompts-and-limits, 3.7-tasks-part-2(3.8)›
- **WD-IDEA-CONT-050** [voice] A scene-instance image is the selected master reference regenerated with the scene's visual description applied, and status tags applied in that same regeneration. For example, a normal SpongeBob master, plus "wears a suit" for this scene and a "soiled" tag because he fell in mud, yields SpongeBob in a muddy suit. ‹src: 3.7-tasks-part-1›
- **WD-IDEA-CONT-051** [idea] Expected state behavior: characters change across an action sequence, becoming sweaty, injured, or determined. Props show wear or activation, such as tools getting dirty or security systems activating. Tags such as "damaged", "activated", and "compromised" apply to these states. A simple scene should need no changes beyond the inherited master descriptions. ‹src: golden-test-evaluation-framework›
- **WD-IDEA-CONT-052** [impl] Assets can evolve across scenes in both directions, such as muddy to clean or injured to healed, while their inheritance chain stays intact. ‹src: development-progress›
- **WD-IDEA-CONT-053** [impl] Only real changes in visual appearance count as transformations. Emotional shifts and dialogue changes do not count. ‹src: system-prompts-inventory›
- **WD-IDEA-CONT-054** [idea] Parentheticals such as "(crying)" or "(bloodied)" inform how a character should look in that scene's visual state. Parenthetical delivery notes also feed voice generation as delivery context (WD-IDEA-STORY-062). ‹src: tiptap-json-extraction-guide›
- **WD-IDEA-CONT-055** [impl] Every change to a scene asset instance is tracked: a modification count, which field changed last, and an optional reason the user can supply for the change. ‹src: development-progress, planning-wif-lawrence›
- **WD-IDEA-CONT-056** [planned] An asset change log records what changed, when, and why. Users can roll an asset back to a previous state, separately from branch-level rollback. ‹src: missing_todos-not-sure›

## Scene-to-scene handoff: end state becomes next start state

- **WD-IDEA-CONT-059** [idea] Assets, including characters, props, and wardrobe, keep their state across scenes. When entering scene N+1, each asset defaults to its final state from scene N. ‹src: project-overview, README›
- **WD-IDEA-CONT-060** [idea] State-inheritance rule: an asset seen in the previous scene starts this scene in its end state from that scene. An asset new to this scene starts from its master definition. Assets needing explicit state changes are flagged. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-061** [impl] From Scene 2 onward, assets are populated in a set order. Assets first inherit from the prior scene, carrying forward their status tags, scene description overrides, and images. Gaps are then filled from the scene's expected dependencies for assets newly appearing in this scene. An instance can also be created from a project asset, detected from shot or script dependencies, or added manually. "Inherit from prior scene" copies the previous scene's asset states into the current scene as a starting point.
- **WD-IDEA-CONT-062** [idea] Scene asset instances are pulled automatically into the local context of the current scene. ‹src: project-overview›
- **WD-IDEA-CONT-063** [voice] Legacy docs describe per-frame attachments, including characters, major props, and location direction shots, as already in the asset library from earlier stages and pulled in automatically. The blocking is the only extra piece added to that per-frame bundle. ‹src: voice-message-5-2›
- **WD-IDEA-CONT-064** [idea] Each scene instance records the scene it inherited from, so an asset's state history can be traced back through earlier scenes. ‹src: architecture-and-rules, database-schema-state-transition-matrix›
- **WD-IDEA-CONT-065** [idea, impl] Each scene instance has a carry-forward toggle, on by default, that decides whether its status tags persist into the next scene. Status tags capture temporary physical state such as "muddy", "torn shirt", "bloody", or "wet", generated during production from shot outcomes. So a character who gets muddy stays muddy, and a broken prop stays broken until something fixes it.
- **WD-IDEA-CONT-066** [idea] Entering scene N+1 after a scene that set carry-forward tags triggers a mandatory question. The system looks up carry-forward tags from Scene N and asks the user, for example: "Character 'John Doe' has status 'muddy' from Scene N. Carry forward to Scene N+1?" ‹src: project-overview, database-schema-state-transition-matrix›
- **WD-IDEA-CONT-067** [idea] State ownership: the scene asset stage (Stage 8) defines only each asset's starting visual state at its first appearance in the scene. Frame generation (Stage 10) owns visual evolution within the scene. No other stage changes asset appearance. ‹src: project-overview, user-flow›
- **WD-IDEA-CONT-068** [idea] Mid-scene visual changes are not pre-defined upstream. Later frame prompts derive them from the action context and the prior frame. Over-specifying visual evolution upstream is explicitly discouraged as brittle. ‹src: project-overview›
- **WD-IDEA-CONT-069** [idea, impl] Each scene stores a prose summary of its final moment and a reference to its final frame, with a thumbnail, so the next scene can pick up visually where it left off. ‹src: architecture-and-rules, database-schema-state-transition-matrix, development-progress›
- **WD-IDEA-CONT-070** [idea] A scene end state contains: the final shot's action and dialogue; the last approved end frame; every asset instance's state (description override, status tags, and carry-forward setting); character positions (e.g., "standing by window") and states (e.g., "facing door"); and the final setting. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-071** [planned, voice] After Stage 10, an AI writes a natural-language end-state summary of how the scene concludes. It covers each character's appearance, position, and emotional state, and what changed for props and locations. It draws on the final shot's action and dialogue, final asset states, and status tags. The summary replaces placeholder data in the rearview mirror and feeds continuity validation, which compares the prior scene's end state with the current scene.
- **WD-IDEA-CONT-072** [idea] When a scene completes, its end state is saved and the pipeline loops back to the scene hub (Stage 6) for Scene N+1. Scene N's end state is passed in as the "previous scene." ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-073** [idea] Three steps consume the scene end state. Shot list generation uses the end frame and character positions so the next scene's first shot connects. Asset relevance uses the asset states to decide whether each asset inherits or reverts to its master. Frame prompting uses the previous scene's end frame as the visual reference for the next scene's first start frame. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-074** [idea, impl] A scene's first shot must visually connect to the previous scene's end state. Character positions and states must match how the prior scene ended. The setting must either match or transition explicitly. ‹src: AI-agent-registry-context-flow-architecture, system-prompts-inventory›
- **WD-IDEA-CONT-075** [idea] Each scene's shot list includes continuity notes explaining how the scene connects to the prior and next scenes. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-076** [impl] Across a scene boundary, the previous scene's end frame and the next scene's start frame are available to each other as adjacent continuity references. ‹src: 3.8-phase5-non-adjacent-continuity›

### Reference chain across scenes

- **WD-IDEA-CONT-078** [planned, impl] Historical reference carousel: a scene asset's reference defaults to the selected image from the most recent prior scene, so scene 4 defaults to scene 3. The user can cycle through the master asset, then the Scene 1 and Scene 2 instances, and so on, and confirm with "Use This Reference."
- **WD-IDEA-CONT-079** [planned] Chain edge cases: the first scene defaults to the master asset, and scenes without a generated instance are skipped. Scene deletion and reordering must be handled. When the previous scene has no instance for an asset, Stage 8 still shows that asset's latest images from earlier scenes as a carousel of past modifications. Any of them can be pulled in as the new reference. The fallback order is scene instance, then master, then placeholder. ‹src: MVP-tasklist-v1.1, Tickets, master-mvp-tasklist›
- **WD-IDEA-CONT-080** [impl, planned, voice] An asset's state is an inheritance chain from the master (Stage 5), through the scene instance (Stage 8), prompts (Stage 9), and frames (Stage 10). Final frames should reflect master and scene assets rather than generic output; frames that ignore them read as generic slop and defeat the purpose, and the requirement covers master and scene-instance assets alike. A reported bug, where master assets did not influence scene and frame generation, must be fixed. ‹src: Tickets, master-mvp-tasklist, 3.7-tasks-part-2(3.8)›
- **WD-IDEA-CONT-081** [voice, planned] Frame generation must receive the scene-specific instance image, for example the gnome variant, not the original master reference. Assets must actually be fed into frame generation, because shot-to-shot continuity comes from using asset images to generate subsequent frames. Scene-specific images from Stage 8 must flow through to final frame generation in Stage 10, so frames resemble the scene instances rather than the masters.
- **WD-IDEA-CONT-082** [planned] Asset reference images are resolved fresh at frame-generation time, rather than trusted from a list cached at prompt time. A cached list can go stale or expire. ‹src: 3.8-phase1-asset-inheritance-fix, 3.8-threads›
- **WD-IDEA-CONT-083** [planned, future] Each scene instance inherits from the prior scene's instance, forming a chain. An asset timeline view shows the asset's visual state evolving across scenes, with tools to validate and repair the chain. Later, a visual tree of the chain is planned to show an asset's inheritance across scenes.

## Story-informed scene state

They describe the asset generally, not the scene conditions (soaked, torn dress, exhausted) that the script, treatment, and beat sheet already imply. ‹src: 3.7-tasks-part-1, 3.7-phase-2-story-context-updates›

- **WD-IDEA-CONT-088** [voice, impl] Bulk results open in a review modal. ## Frame reuse: approved frames become continuity context

- **WD-IDEA-CONT-197** [voice] Regenerating every frame from one vague establishing shot risks completely different-looking environments. Preferred workflow: generate one frame using only the establishing reference (regenerating a few times if needed), then reuse and edit that liked frame through the scene and later scenes. The image-level version of this iterate-then-reuse workflow is WD-IDEA-LOC-112; this bullet applies the same workflow to frames. ‹src: post-clean-location-rethink›
- **WD-IDEA-CONT-198** [planned, voice] A reused prior frame is editable input for the current frame, not just visual inspiration, and this should be easy and obvious. Users drag a previously generated frame (from any shot, earlier or later, in this or other scenes) into the frame they are working on as a background or composition base, even if it was never designated earlier. They then edit it by prompt, for example a character now holding an object, a new character added, blood on the wall, or the room on fire. Only the delta changes, unedited areas stay the same, and old assets are replaced with new ones rather than generating from a blank canvas. Using the pulled-in frame as-is is expected to be rare; mostly it is a starting point. Drag-and-drop is chosen because the user sees exactly what is pulled in, a source-of-truth starting point that keeps many consistencies even when characters, actions, wardrobe, or body language change. ‹src: 5-1-location-system-intent-source, post-clean-location-rethink, streamlined-input-process-consolidated›
- **WD-IDEA-CONT-199** [planned] For each shot, the user chooses one of three paths: reuse or edit an approved frame, generate a variation from a base, or generate fresh. The shot's workspace states its continuity goal (for example, "Preserve kitchen background, change character blocking"), with output actions Generate Variation, Edit From Base, and Generate Fresh Instead. ‹src: 5-3-location-implementation-plan, 5-2-location-product-synthesis›
- **WD-IDEA-CONT-200** [planned, impl] The frame stage suggests ranked continuity bases: earlier approved or generated start frames from the same location, each with a reason (same location, same or similar camera direction) and a suitability level, plus an option to generate fresh. Tiers: strong (same location and direction), usable (same location, no direction conflict), weak (same location, different direction). ‹src: 5-3-location-implementation-plan, 7-19-location-stabilization-master-plan, 8-1-location-continuity-phase-5-6-audit›
- **WD-IDEA-CONT-201** [impl] Candidate ranking for a continuity base prefers frames from the same scene, then approved frames over merely generated ones, with ties broken by recency. The shot's own frames and frames without images are excluded, and a shot with no linked location gets no candidates. ‹src: 7-19-location-stabilization-master-plan, 8-1-location-continuity-phase-5-6-audit›
- **WD-IDEA-CONT-202** [impl] Selecting a continuity base raises the shot's continuity strength. A strong base with no risks yields a "strong" rating. ‹src: 7-19-location-stabilization-master-plan›
- **WD-IDEA-CONT-203** [impl, planned] A selected base becomes the primary reference (location views are supporting context only) and switches the shot into reuse/edit mode, overriding match and camera-change modes. The prompt describes only the delta on top of the base, such as "move camera slightly wider," "replace standing pose with seated pose," or "keep same cabinets, oven, doorway layout." The shot's frame prompt gains an explicit reuse/edit instruction block. ‹src: 7-19-location-stabilization-master-plan, 5-2-location-product-synthesis›
- **WD-IDEA-CONT-204** [impl] Edge case: if the selected base is later deleted, rejected, or loses its image, generation silently falls back to the shot's normal references instead of failing. - **WD-IDEA-CONT-205** [planned] The edit-delta workflow clearly separates what should stay the same from what should change, and shows which background and location references are carried into generation. ‹src: 5-3-location-implementation-plan›
- **WD-IDEA-CONT-206** [planned] An approved output can stay just an output, be promoted to an established view, or later serve as a continuity base for other shots. ‹src: 5-3-location-implementation-plan›

## When upstream things change

- **WD-IDEA-CONT-234** [idea] When an upstream stage is edited, every downstream AI step re-runs with freshly assembled context carrying the edited content and its new version number. Unchanged inputs (project parameters, style capsule, global context, previous frame reference) are reused as-is. ‹src: AI-agent-registry-context-flow-architecture›
- **WD-IDEA-CONT-235** [idea] The end-frame anchor chain makes continuity cascade. A script or production edit in scene N, or regenerating a start or end frame there, marks scene N's video outdated, updates its end frame, and marks every later scene "continuity broken." Editing scene N's shot list after frames or video exist marks its visual, prompt, and video stages (Stages 8-12) outdated and every later scene "continuity broken," and recalculates scene N's frame costs and warns about the downstream impact. This is a high-cost cascade. Invalidation-scope alternatives are WD-IDEA-UX-063 to WD-IDEA-UX-067; this bullet is the high-cost option described in WD-IDEA-UX-066. ‹src: project-overview, database-schema-state-transition-matrix, AI-agent-registry-context-flow-architecture›
