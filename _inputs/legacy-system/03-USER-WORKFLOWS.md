# 03. User workflows (reachable end-to-end)

Scope. This document lists the end-to-end user workflows that the HEAD code of WizardDirector (Aiuteur) makes reachable from the UI, as numbered step lists. Each step gives the UI element, the call chain (UI handler, frontend service, HTTP route, backend service, table or provider), what is persisted, what gates the step, failure and refresh behavior, and the ledger ids that support it. Steps the code cannot complete are marked as dead ends. Workflows covered: sign-up and login, project creation, opening a project and stage navigation, Stage 1 intake (manual modes and Streamline), Stage 2 treatment, Stage 3 beat sheet, Stage 4 master script and scene creation, Stage 5 project assets, Stage 6 Script Hub, Stage 7 shot list, Stage 8 scene asset definition, Stage 9 shot-asset assignment and prompts, Stage 10 frames, Stages 11 and 12 checkout and video, style capsules and the asset library, and a table of every regenerate, retry and revert affordance. Claims that only runtime observation would settle are marked UNKNOWN.

Sources. Ledger kinds CAP (primary), AI, STATE, ROUTE, INVALIDATE, FACT, ENTITY and DEAD as cited by id. The shell and the reports' `path:line` evidence are cited inline. Reports: V1 (shell), V2 (style and library), V3 (narrative), V4 (streamline), V5 (project assets), V6 (scene assets), V7 (continuity and locations), V8 (shots), V9 (prompts and frames), V10 (video and checkout), H (state and invalidation), R1a and R1b (contradiction verification, used as verdicts where they exist).

Reading notes. Document map is 00-README.md. Sibling documents: 01 overview, 02 capabilities, 04 domain and state, 05 data model, 06 writing, 07 assets and continuity, 08 shots, frames and generation, 09 AI and prompts, 10 versioning, locking and invalidation, 11 architecture, 12 async and providers, 13 tests, 14 dead and duplicated code, 15 pressure, 16 coverage and unknowns, 17 ledger. Topics owned by those documents are cross-linked by filename rather than repeated.

## 0. Conventions

- Ledger ids are cited in full (`WD-IMPL-CAP-0013`). Flags (present, reachable, functional, persisted, tested) are not repeated in the tables; read them from `_evidence/merged/merged.jsonl`.
- Status words follow the brief vocabulary: IMPLEMENTED, REACHABLE, FUNCTIONAL, PERSISTED, TESTED, PARTIAL, MOCK-ONLY, DEAD, ORPHANED, LEGACY, DUPLICATED, CONTRADICTED, UNKNOWN.
- "Phase A" means project-level Stages 1 to 5. "Phase B" means per-scene Stages 7 to 12. Stage 6 is the Script Hub. The stage component names are `Stage1InputMode`, `Stage2Treatment`, `Stage3BeatSheet`, `Stage4MasterScript`, `Stage5Assets`, `Stage6ScriptHub`, `Stage7ShotList`, `Stage8VisualDefinition`, `Stage9PromptSegmentation`, `Stage10FrameGeneration`, `Stage11Confirmation`, `Stage12VideoGeneration` (V1 section 5.3).
- Route paths are relative to `/api/projects/:projectId` unless shown in full. Service names are the frontend `src/lib/services/*` modules and backend `backend/src/services/*` modules.
- "Gate" means a condition that stops the step. "Refresh" means what the UI re-reads after the step.
- Per V1 section 5.5, the UI has no loading gate on stage states. Stage components render before the stage-state fetch completes.

#### 4.2.1 What the commit writes

Route `streamline.ts:45-89` builds `payload = {project_id, user_id, stage_transitions, project_config?, stage_1_draft?, assets?, resolutions?, resolution_edits?}`. The backend client uses the service-role key, so RLS is bypassed and ownership is checked only in Node (`config/supabase.ts:10,17`). The RPC runs as one plpgsql call (V4 section 4):

1. Resolve `branch_id = projects.active_branch_id`. A null branch raises.
2. Lock existing `stage_states` rows for stages 1 to 5 with `FOR UPDATE`. Only existing rows are locked.
3. If `project_config` is present: `UPDATE projects` for `project_type`, `content_rating`, `genre`, `tonal_precision`, `target_length_min`, `target_length_max`, `aspect_ratio`, each wrapped in COALESCE. Frontend sends minutes multiplied by 60 (`Stage1InputMode.tsx:456-464`). `writing_style_capsule_id` is NOT written (WD-IMPL-CAP-0065 interacts; see workflow 15). The `audio-visual` value fails the CHECK here too (R1a C09).
4. If `stage_1_draft` is present: `INSERT stage_states` stage 1 `draft`, origin `COALESCE(origin, 'authored')`, content = full Stage 1 content. Migration 044 strips this key before delegating, so this block does not run through the wrapper (V4 section 4 step 5 note).
5. Stage transitions, ascending 1 to 5 (`043:137-460`):
   - `'skip'`: stage must be 2, 3 or 4. Raises if latest row is `locked`, or if stage n-1 is not locked or skipped. INSERT `skipped`, origin `skipped`, content `{}`.
   - `'locked'`: raises if no row exists. For n > 1, stage n-1 must be locked or skipped. INSERT a copy of the latest content with status `locked`, origin `COALESCE(current_origin, 'authored')`.
   - Object form `{status, content, origin, regenerationGuidance}`: validated. No check that the stage is already locked, so existing locked content is superseded by a new version.
   - Every inserted row has `version = latest + 1`, `created_by = user_id`, `inherited_from_stage_id = NULL`.
6. `assets[]`: INSERT `project_assets` (`name`, `asset_type`, `description`, `image_key_url`, `locked FALSE`, `source` default `streamline_import` (FE sends `streamline_import` for image cards and `extracted` for note drafts, `Stage1InputMode.tsx:466-472`), `scene_numbers '{}'`). No dedupe against existing assets (WD-IMPL-CAP-0125; V5 `project_assets` appended).
7. `resolutions[]`: INSERT `intake_resolutions` (question text, category, options, `selected_answer`, `answer_source`, subject, conflicting sources). Client-id to uuid map built here.
8. `resolution_edits[]`: INSERT `intake_resolution_edits`. An unknown `resolution_client_id` raises.
9. `UPDATE projects SET updated_at`. Returns `{success, project_id, branch_id, stages[], assets[], resolutions[]}`. The frontend type omits assets and resolutions, and the caller ignores the result (`streamlineService.ts:18-23`).

Routing produces these transitions from the material (`streamlineRouting.ts:53-155`; first match of each type wins):

| Material | Stage 1 | Stage 2 | Stage 3 | Stage 4 | Lands on |
|---|---|---|---|---|---|
| Usable script (plus optional treatment and beat sheet) | locked | treatment ? locked (imported) : skip | beat ? locked (imported) : skip | locked (imported), content `{formattedScript, tiptapDoc, scenes: [], syncStatus 'synced'}` | 5 |
| Beat sheet, no script | locked | treatment ? locked : skip | locked (imported) | none | 4 |
| Treatment only | locked | locked (imported) | none | none | 3 |
| Notes or images only | locked | none | none | none | 2 |
| Nothing routable, or config incomplete | blocked (`canConfirm` false) | | | | |

Stage 2 content is `{variations:[{id 'sf-<fileId>', content: formattedText ?? text, structuralEmphasis 'balanced', estimatedRuntimeSeconds 0}], activeVariation 0}` (`streamlineRouting.ts:167-173`). Stage 3 content is the AI-formatted beats, or one beat holding raw text with `narrativeStructure 'imported_as_single_beat'` (`:175-190`). Neither writes `processedInput` (V4 section 4).

#### 4.2.2 Existing content on commit, and retry

- Stage rows are append-only. Imported content supersedes older locked content for stages 2 to 4 because latest-version reads win (`stageStates.ts:26-34`). The only overwrite guard is the skip guard: skipping over a locked stage raises.
- Stage 1 always receives two new rows per commit (draft, then locked copy), even if Stage 1 was already locked (V4 section 5).
- `project_assets`, `intake_resolutions`, `intake_resolution_edits` are appended. Committing twice inserts duplicates (WD-IMPL-CAP-0125; V4 section 5).
- Phase B and Stage 5 are not invalidated by a commit (V4 section 4).
- Retry after a server-side success (for example, the post-RPC scene step failed, or the network dropped after commit): the RPC has no idempotency key and no existence check, so a second confirm inserts new stage versions, new `project_assets` rows, new `intake_resolutions` rows, and re-skips over `skipped` rows (R1b C19 CONFIRMED; V4 section 9).

Scene creation rules (from `frontend/src/lib/services/scriptService.ts` and `projects.ts`):

- Heading regex per trimmed line: `^(INT\.|EXT\.)\s+(.+?)(?:\s*-\s*(DAY|NIGHT|CONTINUOUS|LATER|MOMENTS LATER|DAWN|DUSK|MORNING|AFTERNOON|EVENING))?$`, case-insensitive (`scriptService.ts:378`). `INT./EXT.`, `I/E.`, `INT.HOUSE` (no space), and `EST.` are not headings (V3 section 6.1).

### 7.3 Effect of re-approval on existing scenes

Matching is positional. Existing work (shots, frames, video jobs, scene asset instances, `stage_locks`, deferral, end state) stays attached to the row ID, and the row ID is re-pointed at different narrative content when the script changes. Derived from the matching rules in A3 and the cascade foreign keys below (V3 section 6.3; R1b C15 PARTIALLY CONFIRMED).

| Scenario | Row identity | Text | Downstream work |
|---|---|---|---|
| Identical re-approve | Preserved (`slug:number` match) | Same (already normalized) | Untouched. `updated_at` and `dependencies_extracted_at` bumped |
| Edit text inside scene k | Preserved | Excerpt k replaced | Untouched. No status change, `stage_locks` unchanged |
| Change heading of scene k | Preserved through number fallback | Slug and excerpt replaced | Untouched |
| Insert a scene at position k | Rows 1 to N keep IDs by number. A new row N+1 is inserted. | Row k now holds the inserted scene. Each later row holds the previous scene's text. | Work on rows k to N now sits against different text. Old scene N's work stays on row N, which now holds old scene N-1's text. The new row starts empty. |
| Delete scene k | Rows matched by number. Row N is deleted. | Rows k onward shift up. | Old scene N's shots, frames, video jobs and asset instances CASCADE-delete. Scene k's work stays on the row that now holds old scene k+1's text. |
| Reorder scenes | Matched by number | Content permuted | Production work stays with positions, not with stories |
| Script with zero headings | Blocked client-side ("No scenes found") | | |

Cascade foreign keys with `ON DELETE CASCADE` from `scenes(id)` (V3 section 6.3, verified by R1b C15): `shots` (`006:7`), `image_generation_jobs` (`007:13`), `scene_asset_instances` (`015:15`), `video_generation_jobs` (`021:10`), `scene_asset_suggestions` (`024:6`), `transformation_events` (`030:17`), and `039:88`. ### 10.3 Transformation semantics

- Model: `instant` (switch at the trigger shot), `within_shot` (the trigger shot is still pre but flagged transforming; post from the next shot), `gradual` (pre until the completion shot; post at or after it). Resolution happens in `resolveOverridesForShot` (`transformationEventService.ts:107-201`) over confirmed events only, sorted by trigger `shot_order`, cumulative (V6 section 8.1). Gradual events with a NULL completion shot never reach post (for example after the completion shot is deleted).
- Effects: frame and video prompt generation apply the resolution per shot in the same scene (`routes/frames.ts:600-617`, `promptGenerationService.ts:1075`, `routes/projects.ts:3788-3800`). Stage 10 reads confirmed events for reference images (`frames.ts:1719-1727`). Later scenes see a transformation only when inheritance runs after the confirm (E1). A later confirm in scene N does not change an instance already created in N+1 (V6 section 8.4).
- Automatic detection is not wired. Stage 7 shot extraction writes `shots.transformation_flags`, and no code reads it to create events. `detected_by` values `stage7_extraction` and `stage8_relevance` are never produced, so the "AI Detected" branch is unreachable (WD-IMPL-CAP-0192 CORRECTED by R1b C18; R1b C18 PARTIALLY CONFIRMED).

### 10.4 Lock semantics in Stage 8 (V6 section 6.3)

Five notions of "locked" coexist:

1. Scene stage lock for stage 8 (`scenes.stage_locks['8']`). Set by Proceed (E23). Inside Stage 8 it only suppresses auto-populate and shows `LockedStageHeader`. No backend route checks it (V6 section 6.3, item 1).
2. The `'locked'` status tag (E7). It is a literal string in `status_tags`, reaches image prompts and prompt-generation tag lists, and carries forward to the next scene.
3. The list badge "locked" (`SceneAssetListPanel.tsx:60-64`) is computed from `image_key_url` and `modification_count`, so it is unrelated to the other notions. A separate `reviewStatus()` keyed off the tag is DEAD (CONTRADICTED).
4. `project_assets.locked` (Stage 5). Used to filter AI relevance candidates and bootstrap. Stage 8 creation (R13) sets it true.
5. `transformation_events.confirmed`. Only confirmed events feed resolution, inheritance, the reference chain and Stage 10. No un-confirm route.

### 10.5 Dead ends and broken steps (Stage 8)

- Detect with AI fails as a whole when any asset already exists in the scene: R3 returns 409 for that asset, `Promise.all` rejects, the user sees "AI detection failed" although others were created, and suggestions are not saved (V6 section 3).
- Inheritance from scene N-2 never happens. An asset absent in N-1 is not inherited, although the relevance prompt uses a "last appearance anywhere earlier" lookup (V6 section 3).
- Locked instances stay editable through image routes, master reference, upload and bulk context. The `'locked'` tag does not lock the instance (E7, E8, E13, E16).
- `handleDetectAndPopulateAssets` is DEAD (V6 section 17).
- Carry-forward and tag prompt state is per browser (localStorage) (E6).
- Inherited tags from a transformed asset become `[]`, because `post_status_tags` is never populated by the UI (V6 section 8.4).
- Bulk generation does not skip `use_master_as_is` instances (E9).
- `use_master_as_is` can be turned on but not off, except by selecting a different master reference (E11).
- Scene asset image jobs are not awaited. A server restart loses in-flight jobs and the client timeout does not stop them (E8).
- Transformation events have no un-confirm path, and the Stage 8 Proceed gate counts can be stale (E21, E23).
- Routes R23 to R29 have no project ownership or scene membership check (V6 section 15). R5 loads the instance by id without a scene or project check.
- Suggestions have no de-duplication, and "Add from library" never links them (E18).
- DEAD and ORPHANED items: `UseMasterAsIsCheckbox`, `handleSaveDescription`, `typeIcons` and related constants, `assetFilters` state, `AssetInheritanceService.getInheritanceChain`, `shots.transformation_flags` (write-only), `scene_asset_suggestions.asset_id`, and R8 `imageKeyUrl` (V6 section 17).

### 11.1 Validation gate (lock)

`ShotValidationService.validateShots` (`shotValidationService.ts:41-193`) runs only in the lock route:

- Errors (block lock, 400): zero shots; duplicate `shot_id`; empty action, setting or camera; duration below 1 or above 30 seconds.
- Warnings (409 unless `force`): duration below 4 or above 12; foreground characters not in `scenes.expected_characters` (Levenshtein suggestion under 3, only when the expected list exists); total duration below `shots*4` or above `shots*15`; location continuity summary when any location is unresolved, ambiguous or mismatched (`projects.ts:173-188, 2930-2939`).
- Background characters are not checked. The client mirror (`Stage7ShotList.tsx:549-622`) has no character check, so character warnings surface only through the server 409 (V8 section 5).

### 11.2 Shot data that is written but not read

- `shots.transformation_flags` is written by extraction (`projects.ts:1928`) and returned by GET shots, but no code reads it to create transformation events. The "AI Detected" branch is unreachable (WD-IMPL-CAP-0192 CORRECTED by R1b; R1b C18 PARTIALLY CONFIRMED). The correction is recorded in section 0.
- `continuity_flags` are written by extraction, split and merge, editable through PUT, and not shown in the Stage 7 UI (V8 section 1).
- `Shot.transformationFlags` is declared in the frontend type and never populated (V8 section 11).

### 11.3 Dead ends and broken steps (Stage 7)

- No manual shot creation route or UI. Stage 7 imports a `Plus` icon but renders no add button (V8 section 2.2).
- Re-extraction is effectively unreachable from the UI, and the server does not guard it. A second extract on a scene with shots would hit `UNIQUE(scene_id, shot_id)` (inferred, V8 contradictions C6).
- Stage 7 lock does not gate shot mutations. No shot mutation route checks `shot_list_locked_at` or `stage_locks` (R1a C05 CONFIRMED; WD-IMPL-INVALIDATE-0055). Direct API calls can change a locked scene's shots, and Stage 9 split can mutate shots of a locked Stage 7 (V8 section 6).
- The `stage_locks` column exists only in `backend/quickies-sql/add_stage_locks.sql` (R1a C04 CONFIRMED). Lock routes return 404 for every scene on a database without the column (R1a C04).
- Shot lock, unlock and relock are DUPLICATED: lock is written three times per action, and two lock stores disagree in principle (`shot_list_locked_at` vs `stage_locks['7']`) (V8 section 11).
- Split and merge do not reflect shot-structure changes on prompts or frames. Merge does not invalidate Stage 9 or later (V8 contradictions C4).
- Delete does not compact `shot_order`, so merge's neighbour lookup breaks after a gap (V8 contradictions C9).
- The shot-assignment bulk template calls `DELETE .../shot-assignments/all`, which Express routes to the single-delete handler because it is registered first. The bulk path fails before creating any assignments (R1a C06 CONFIRMED). This affects Stage 9 (section 12).
- Legacy unlock invalidation (`frames.status 'invalidated'`, `videos`, `invalidation_logs`) cannot be reached from the UI, and the frames status value is not in the CHECK constraint (V8 section 6, R1a C04 cross-slice).

### 15.6 Dead ends and broken steps (style and library)

- The capsule list endpoint returns summary columns only, so cards and selector previews show names and badges without labels, excerpts, pillars or images (K1; V2 section 2).
- Favorites and duplicates act on shared preset rows. Toggling a preset favorite changes it for every user (K8, K9; V2 section 1.3).
- Deleting a used capsule is expected to fail on foreign keys with a 500 (K7; inferred, UNKNOWN at runtime).
- Project capsule columns are never written, so Stage 9, end-frame and continuity prompts carry "No visual style capsule applied." (I5; R1a C02 CONFIRMED).
- Frame image jobs carry no capsule id, text or images (I7; R1a C01 CONFIRMED).
- Changing style does not unlock Stage 5. The row stays `locked`, and only the style keys are cleared through autosave (CS1; H FACT-06). V5 section 9 describes the change as an unlock, which this document corrects.
- The global asset capsule selector cannot clear a capsule (G2), and an `extra_archetype` global asset crashes `AssetCard` (V2 contradictions 11).
- Promote creates duplicate global assets and does not link the source (G5).
- Role-less capsule images change which NanoBanana prompt branch runs (I4; V2 section 4 row 7).
